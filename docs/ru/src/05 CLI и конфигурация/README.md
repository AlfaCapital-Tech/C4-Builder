# CLI и конфигурация

## Команды

| Команда | Что делает |
|---|---|
| `c4builder` | собирает проект в текущей папке; без конфига сначала запускает мастер, без терминала — ошибка с кодом 1 |
| `c4builder new` | создаёт проект из шаблона в новой папке |
| `c4builder new --name demo -y` | то же без вопросов: полный конфиг со значениями по умолчанию |
| `c4builder config` | мастер настройки с текущими значениями |
| `c4builder site` | собирает и раздаёт сайт локально |
| `c4builder site -w` | то же с пересборкой на каждое сохранение и перезагрузкой браузера |
| `c4builder feedback --wait --as <имя>` | ждёт следующую пачку замечаний агенту `<имя>` со страницы `site -w` и печатает её, см. «Замечания агенту» ниже |
| `c4builder status [--json]` | работает ли dev-сервер этого проекта: адрес, pid, агентский режим, слушатели `feedback`; код 0 — работает, 1 — нет, см. «Файл состояния и `c4builder status`» ниже |
| `c4builder check <файлы...>` | проверяет диаграммы `.puml`, `.iuml`, `.d2`, `.bpmn`, `.mmd`, `.wireflow.json` без сборки, код выхода 0 или 1; `--strict` — 1 и при предупреждениях; `--format json\|github\|gitlab` — отчёт для агента и CI, `--files-from <файл>` — список путей из файла или stdin (см. «Проверка диаграмм» ниже и [Диаграммы](03%20Диаграммы/03%20Диаграммы.md)) |
| `c4builder jre info` | параметры managed-JRE для внешних кэшей в CI (JSON) |
| `c4builder jre install [--force]` | скачать JRE в кэш заранее; `--force` — даже если есть системная Java |
| `c4builder list` | показать текущий конфиг; с 0.5.0 вне проекта — ошибка с кодом 1, файлов не создаёт |
| `c4builder reset` | очистить конфиг проекта; с 0.5.0 вне проекта — ошибка с кодом 1 |
| `c4builder docs` | краткая справка по ключам конфига и адрес этой документации |
| `c4builder update` | обновляет глобальную npm-установку до новейшей версии, иначе печатает, как обновиться, см. «Обновление» ниже |
| `c4builder skills` | ставит или обновляет скиллы агентов той же версии, что и CLI, в текущий каталог: `.agents/skills/`, под Claude Code — и `.claude/skills/`; конфиг проекта не нужен, см. «Скиллы для агентов» на странице [Агенты](08%20Агенты/08%20Агенты.md) |
| `c4builder doctor [группа...]` | диагностика: среда, скиллы агента, пробный рендер, проект и порт; только читает, работает вне проекта и без терминала, см. «Диагностика» ниже |
| `c4builder help [команда]` | общая справка или справка команды, см. «Справка» ниже |

Каноническая форма — позиционные команды: `check`, `jre`, `site`, `new`, `config`, `update`,
`feedback`, `skills`, `doctor`, `status`, `list`, `reset`, `docs`, `help`. Флаговые формы `--site`, `--new`,
`--config`, `--list`, `--reset`, `--docs` работают как синонимы, но в справке не показываются (в
0.4.0 есть только они). Любой другой позиционный аргумент — ошибка `unknown command` с кодом 1:
опечатка (`c4builder nwe`) не запускает сборку.

### Справка

`c4builder --help` (`-h`, `c4builder help`) печатает, что делает запуск без команды, список команд
и только глобальные флаги. `c4builder <команда> --help` (`-h`, `c4builder help <команда>`) —
справку этой команды: назначение, строку использования, её флаги, формат вывода, коды возврата и
примеры. Справка печатается в stdout с кодом 0, работает в любом каталоге и без терминала, ничего
не создаёт и не скачивает (`c4builder jre install --help` не качает JRE) и не печатает уведомление
о новой версии; для неизвестной команды (`c4builder help serve`) — ошибка `unknown command` с
кодом 1.

Глобальные флаги:

| Флаг | Значение |
|---|---|
| `-c, --config-file <путь>` | другой файл конфига вместо `.c4builder` |
| `-w, --watch` | пересобирать при изменениях в исходниках и папках плагинов |
| `-p, --port <n>` | порт локального сайта для `site` (по умолчанию `webPort` из конфига, 3000); для `feedback`, `doctor` и `status` — порт работающего сайта, по умолчанию — из файла состояния сервера, иначе `webPort` |
| `--system-fonts` | рендер системными шрифтами на один запуск |
| `-v, --verbose` | для сборки и `check`: полный вывод движка и стек при ошибке диаграммы (то же — `DEBUG=c4builder`), см. «Ошибки диаграмм в сборке» ниже; для `doctor` — абсолютные пути и детали |
| `-V, --version` | версия |
| `-h, --help` | справка; с командой — справка команды |

Флаги команд:

| Команда | Флаг | Значение |
|---|---|---|
| `site` | `-o, --open` | открыть главную страницу сайта в браузере |
| `site` | `--open-change <id>` | открыть в браузере страницу change'а OpenSpec по короткому адресу `#/change/<id>` (см. [Плагины](06%20Плагины/06%20Плагины.md)); такого адреса на сайте нет — предупреждение в stderr, адрес всё равно открывается |
| `site` | `--agent`, `--no-agent` | включить или выключить агентский режим `site -w` вне зависимости от окружения |
| `new` | `--name <имя>` | имя проекта, без вопроса о нём |
| `new` | `-y, --yes` | без вопросов: значения по умолчанию (нужен `--name`) |
| `jre install` | `--force` | скачать JRE, даже если есть подходящая системная Java |
| `feedback` | `--wait` | ждать следующую пачку, а не только проверить очередь |
| `feedback` | `--as <имя>` | обязателен: имя слушателя — change или задача агента (1–64 символа: латиница, цифры, `.`, `_`, `-`) |
| `check` | `--strict` | код 1 и при предупреждениях |
| `check` | `--format <формат>` | `text` (по умолчанию), `json`, `github`, `gitlab`, см. «Проверка диаграмм» ниже |
| `check` | `--json` | то же, что `--format json` |
| `check` | `--files-from <файл>` | ещё и пути из файла, по одному на строку; `-` — stdin |
| `status` | `--json` | один JSON-объект, см. «Файл состояния и `c4builder status`» ниже |
| `doctor` | `--json`, `-v, --verbose`, `--strict`, `--full`, `--offline` | см. «Диагностика» ниже |

## Ошибки диаграмм в сборке

Сборка без `-w` (`c4builder`, `c4builder site`) рендерит все диаграммы и печатает каждую
сломанную одной строкой в stderr — тем же текстом, что `c4builder check` для этого файла:

```text
✗ src/dangling.puml: line 4: Fatal parsing error

build aborted — the previous build is backed up in ./docs_bk
```

- Номер строки — от начала файла, с 1. В файле с несколькими `@startuml` и во включаемых через
  `!include` файлах позиция считается от начала блока; у диаграммы-блока в markdown — внутри
  блока, а рядом с путём страницы стоит имя картинки: `✗ src/README.md (README-1a2b3c4d.svg): …`.
- Перечисляются все сломанные диаграммы за один прогон, корректные дорендериваются и попадают в
  кэш. Затем `build aborted — …` (если есть прошлый выход, он остаётся в `docs_bk`) и код
  выхода 1 — без стектрейса Java и Node.
- Нет Java или упал поток рендера — сборка останавливается сразу, сообщение одно на все диаграммы;
  ошибки других диаграмм, найденные до этого, печатаются вместе с ним.
- `-v, --verbose` или переменная окружения `DEBUG` со значением `c4builder` (список через запятую
  или пробел, `*` — всё) добавляют после строк `✗` полный вывод движка и стек каждой ошибки — то,
  что стоит приложить к issue.
- ASCII-баннер и очистка экрана — только в терминале: в CI, логе агента и файле их нет.

Мягкие ошибки — заглушка вместо битого блока в markdown (`⚠`) и ошибки в `site -w` (`✗`) —
печатаются в stderr тем же коротким текстом, с `-v` — и полным выводом движка. На картинке-заглушке —
та же суть ошибки, а у сбоя процесса PlantUML без позиции — хвост его вывода.

## Dev-сервер `site -w`

`c4builder site -w` поднимает сайт сразу после компоновки страниц, не дожидаясь рендера
диаграмм. Диаграммы, которых нет в кэше (чистый клон, первая сборка в CI-превью), получают на
своём месте картинку-заглушку `rendering…`, а рендер идёт в фоне после строки `serving your
docsify site`:

```text
serving your docsify site
go to http://localhost:3000
rendering 179 diagrams in background…
rendered 179 diagrams in 118.4 s
```

- Диаграммы открытой в браузере страницы рендерятся первыми: страница сообщает серверу о каждом
  переходе, и он поднимает её диаграммы в начало очереди. Запросы `.md`, которые делает поиск
  docsify для своего индекса, очередь не трогают.
- BPMN и mermaid рендерятся в отдельном потоке (worker thread): пока они рисуются, сервер
  продолжает отвечать на запросы и слать события страницам. PlantUML и так работает отдельными
  процессами java.
- По готовности каждая картинка подменяется на открытой странице без перезагрузки и без потери
  прокрутки. По окончании очереди сервер делает обычную пересборку (всё уже в кэше — доли
  секунды) и перезагружает страницы: так встроенные диаграммы (`embedDiagram`), complete-документ
  и `llms-full.txt` получают готовые картинки, а правки исходников, сделанные во время рендера,
  попадают в сайт. Готовые картинки показываются и при возврате на страницу, где была заглушка.
- Ошибка рендера в фоне не останавливает сервер: на месте диаграммы — заглушка с текстом ошибки,
  в логе — `✗ <файл>: line <N>: <сообщение>`, как у `check`. Пока вход диаграммы (файл и его include/импорты) не
  изменился, пересборки этого запуска её не рендерят заново — переносят заглушку и пишут серую
  строку `unchanged since it failed, not re-rendered`. Исправление файла запускает обычную
  пересборку с рендером; новый запуск `site -w` пробует все упавшие снова.
- Тёплый старт (всё в кэше) заглушек не создаёт и ничего в фоне не рендерит.

Выход `-w` — для просмотра, а не для публикации: если остановить сервер до конца фоновой очереди,
в `distFolder` останутся заглушки (чексумм для них нет, следующая сборка их перерисует). Сборка
без `-w` — в том числе `c4builder site` — по-прежнему ждёт рендера всех диаграмм и падает, если
хотя бы одна не отрендерилась.

Порт фиксирован: `-p` или `webPort`. Занят — сервер не стартует и завершается с кодом 1,
подсказывая свободный из следующих портов: `port 3000 is already in use — pass a different one,
e.g. -p 3001` (свободного среди них нет — `… with -p <port>`). Сам на другой порт сервер не
переходит: перезапустите его с подсказанным `-p` — `feedback`, `doctor` и `status` найдут сервер по
файлу состояния без `-p`.

### Файл состояния и `c4builder status`

Запущенный сервер (`c4builder site` и `--site [-w]`) пишет рядом с конфигом файл
`.c4builder.server.json` (для `-c other.c4builder` — `other.c4builder.server.json`):

```json
{
  "port": 3001,
  "url": "http://localhost:3001",
  "pid": 12345,
  "version": "0.15.0",
  "watch": true,
  "startedAt": "2026-11-07T10:00:00.000Z"
}
```

Файл удаляется при остановке сервера — Ctrl+C, `SIGTERM`, обычный выход (`SIGHUP` сервер не
перехватывает: под `nohup` он, как и раньше, переживает закрытие терминала). Файл от убитого процесса
(`kill -9`, падение) недействителен: действительным его делает только сервер на этом порту,
ответивший тем же `pid`, — и следующий запуск его перезапишет. Пересборок `-w` файл не вызывает.
Добавьте `.c4builder.server.json` в `.gitignore` проекта; в шаблоне `c4builder new` строка уже
есть. Каталог только для чтения — одна строка предупреждения, сервер работает, а команды берут
порт из `-p` или `webPort`.

По файлу команды находят сервер своего проекта без `-p`: `feedback`, `doctor runtime` и `status`
берут порт из `-p`, иначе из действительного файла состояния, иначе из `webPort`.

Один сервер на конфиг: пока сервер работает, повторный `c4builder site` или `site -w` не
собирает сайт и не поднимает второй сервер — печатает `c4builder site is already running for this
project at http://localhost:3001 (pid 12345)` и выходит с кодом 1. С `--open` или
`--open-change <id>` он открывает соответствующий адрес работающего сервера в браузере и выходит с
кодом 0. Сервер с другим конфигом (`-c`) поднимается как обычно, а другой `-p` с тем же конфигом
второй сервер не поднимает: оба писали бы в один `distFolder`. Если запрошен `-w` (или `--agent`),
а работающий сервер запущен без `-w`, повторный запуск выходит с кодом 1 и советом остановить его и
запустить `c4builder site -w` — даже с `--open`.

`c4builder status` — работает ли сервер этого проекта:

```text
site is running at http://localhost:3001 (pid 12345, c4builder 0.15.0, watch)
agent mode: on (claude-code)
listeners:
  add-dark-mode — listening, 0 queued
```

Код 0 — сервер работает, 1 — нет (`no c4builder site on http://localhost:3000 — …`). `--json`
печатает один объект `{ running, url, port, source, pid, version, watch, agent, listeners,
unaddressed }`, без сервера — `{ running: false, port, source, busy }`: `source` — откуда взят
порт (`flag`, `state`, `config`), `busy` — порт занят чужим процессом. Сервер прежней версии (без
файла состояния) — `site is running at …` без подробностей.

Сервер на порту считается сервером проекта, только если он сообщает тот же конфиг (realpath
`.c4builder`): соседний worktree с тем же `webPort` видит чужой сайт как `no c4builder site of this
project on http://localhost:3000 — the port is used by the c4builder site of another project
(<путь>)` с кодом 1 (в JSON — `busy: true` и `otherProject`), `feedback` к нему не подключается, а
`doctor runtime` предупреждает. Сервер из файла состояния жив, но не ответил за секунду (занят
сборкой) — `site is running at … but did not answer in time`, код 0, в JSON — `"responding": false`.
Команда только читает: вне проекта
проверяет порт по умолчанию и файлов не создаёт.

## Обновление

Раз в сутки c4builder в фоне спрашивает npm-реестр, вышла ли новая версия. Запрос делает
`npm view` с реестром, прокси и сертификатами из вашего npmrc — тем же путём, каким потом
ставится обновление. Запуск проверку не ждёт и от сети не зависит: ответ сохраняется в
`~/.config/c4builder/dist-tags.json` (`$XDG_CONFIG_HOME/c4builder/`, если переменная задана)
и используется со следующего запуска. Стабильная версия сравнивается с `latest`, релиз-кандидат —
с бо́льшей из `latest` и `rc`.

Если известна версия новее, в конце запуска в stderr печатается одна строка:

```text
c4builder 0.6.0 is available (current 0.5.1). Run: c4builder update
```

В `c4builder site -w` о новой версии сообщает закрываемая плашка в углу страницы; в файлы сборки
она не попадает.

`c4builder update` при глобальной установке (`npm i -g`) ставит новейшую версию и показывает
вывод npm. Иначе ничего не ставит, печатает команду обновления и завершается с кодом 1: для
зависимости проекта — `npm i -D`, в Docker-образе — `docker pull`.

Проверка и уведомления выключены, если задана переменная `CI` (её ставят GitLab CI, GitHub
Actions и большинство CI-систем) или `NO_UPDATE_NOTIFIER`, а также в Docker-образе. Отключить
на своей машине: `NO_UPDATE_NOTIFIER=1`.

## Проверка диаграмм

`c4builder check <файлы...>` проверяет диаграммы тем же движком, что и сборка, без проекта и
`.c4builder`. По умолчанию вывод текстовый: `✓ <файл>` в stdout, `✗ <файл>: <проблема>` и
предупреждения `⚠ <файл>: <сообщение>` — в stderr. Форма проблемы своя у каждого движка
(см. [Диаграммы](03%20Диаграммы/03%20Диаграммы.md)). Для агентов и CI есть машинные форматы:

| `--format` | Вывод в stdout |
|---|---|
| `text` | по умолчанию, вывод как выше |
| `json` | JSON-массив замечаний по всем файлам в порядке проверки; нет замечаний — `[]`; пути относительно текущего каталога |
| `github` | по строке на замечание — workflow-команда `::error` / `::warning`; GitHub Actions показывает их аннотациями в diff PR; пути относительно `GITHUB_WORKSPACE` |
| `gitlab` | отчёт GitLab Code Quality (`description`, `check_name`, `fingerprint`, `severity`, `location`) для `artifacts: reports: codequality`; пути относительно `CI_PROJECT_DIR` |

`--json` — то же, что `--format json`. Другое значение `--format` — ошибка со списком форматов и
код 1. `--format` и `--files-from` есть только у `check`: с другой командой или сборкой они —
ошибка с кодом 1 (у `doctor` машинный вывод — `--json`).

`--files-from <файл>` добавляет к аргументам пути из файла, по одному на строку; `-` — stdin,
пустые строки пропускаются. Так список изменённых файлов из `git diff` уходит в `check` одним
вызовом — и одним отчётом. `xargs` для машинного формата не годится: длинный список он делит на
несколько вызовов, и в stdout оказались бы несколько JSON-массивов подряд. Пустой список —
пустой отчёт и код 0, в `text` — тоже код 0 без вывода. `--format` и `--files-from` — с
c4builder 0.15.0.

Замечание в `json` — одинаковые поля для всех движков; если у движка поля нет, значение `null`:

```json
[
  {
    "file": "src/context.puml",
    "line": 6,
    "column": null,
    "engine": "plantuml",
    "severity": "warning",
    "rule": "undeclared-element",
    "element": "nope",
    "message": "Rel to undeclared element \"nope\""
  }
]
```

| Поле | Значение |
|---|---|
| `file` | путь с `/`; у ошибки D2 в импортированном файле — путь этого файла |
| `line`, `column` | позиция с 1, которую сообщил движок, — и когда он вписывает её в текст ошибки (XML BPMN, JSON wireflow, mermaid). У нарушения по элементу BPMN и wireflow движок даёт только id — позицию `check` находит по объявлению `id` в исходнике |
| `engine` | `plantuml`, `d2`, `bpmn`, `mermaid`, `wireflow`; `null` — неподдерживаемое расширение |
| `severity` | `error` или `warning` |
| `rule` | правило: bpmnlint (`no-disconnected`), раскладки BPMN (`layout:…`), `undeclared-element` у связи C4 на необъявленный алиас |
| `element` | id элемента BPMN, узла или ребра wireflow, алиас связи C4 |
| `message` | текст замечания без позиции: ни префикса `line N:`, ни строки и колонки, вписанных движком в текст. id элемента BPMN — только в `element`; у wireflow (`edge "e1": …`) и связи C4 id остаётся в тексте: вид узла и макрос значимы для чтения |

Аннотация `github`: `::error file=src/context.puml,line=6,title=c4builder plantuml::Syntax Error`.
В `title` — движок и правило в скобках, текст — сообщение с префиксом `<id>: `, если id не
входит в него по форме движка (bpmnlint). `fingerprint` в `gitlab` не зависит от номера строки:
позиции нет ни в хэше, ни в `message`, и строка, вставленная выше, не делает замечание новым в
виджете MR. Одинаковые замечания — например, ошибка в общем импортируемом `.d2` при проверке
нескольких файлов — попадают в отчёт один раз.

В машинных форматах stdout содержит только отчёт: строк `✓`/`✗`/`⚠` и цвета нет, сообщения о
выборе и загрузке JRE уходят в stderr. Код возврата от формата не зависит: 0 или 1 как в
`text`, `--strict` действует так же. Без файлов машинный формат печатает пустой отчёт (`[]`, у
`github` — ничего) и завершается с кодом 0: джоба над списком изменённых файлов проходит, если
диаграммы не менялись. `text` без файлов и без `--files-from` по-прежнему печатает строку
использования и код 1.

## Диагностика

`c4builder doctor` одной командой показывает, что мешает работе, и под каждой проблемой — строку
`fix:` с командой или ссылкой. Команда только читает: ничего не ставит и не скачивает (JRE тоже),
конфиг не трогает и мастер не запускает. Работает в любом каталоге, в CI и под агентом.

```text
c4builder doctor 0.14.0 (latest)
Environment
  ✓ Node.js 24.11.0
  ✓ c4builder 0.14.0 (latest)
  ✓ no newer version
  ✓ global npm
  ✓ Java 21 (system)
  – no .d2 files in the project
  ✓ bundled font Nimbus Sans
  ✓ no proxy variables set
Skills (claude-code)
  ✓ .agents/skills — 0.14.0
  ✗ .claude/skills — from 0.12.0, CLI 0.14.0
      fix: c4builder skills   (ask the user first)
  – what the agent session loaded is not visible to the CLI
Render
  ✓ PlantUML with C4 in 0.9 s
Project
  ✓ .c4builder valid
  ✓ non-interactive build ready
  ✓ rootFolder src and plugin paths exist
Runtime
  ✓ port 3000 free
  ✓ coding agent claude-code, agent mode on
1 error, 0 warnings
```

Статусы: `✓` ok, `!` предупреждение, `✗` ошибка, `–` проверка неприменима или не выполнена (нет
сети, нет `.d2` в проекте). `(ask the user first)` — исправление меняет файлы проекта или удаляет
личную копию скилла: агент выполняет его только с согласия человека.

| Группа | Проверки |
|---|---|
| `env` | `env.node` — Node.js не ниже `engines` пакета; `env.cli` — версия и канал; `env.update` — вышла ли новая версия; `env.install` — как установлен c4builder, несколько `c4builder` в `PATH`; `env.java` — системная Java 17+ или JRE в кэше; `env.d2` — движок D2, если в проекте есть `.d2`; `env.fonts` — `useSystemFonts`; `env.proxy` — заданы ли `HTTPS_PROXY`, `HTTP_PROXY`, `NODE_EXTRA_CA_CERTS` и есть ли файл сертификатов |
| `skills` | скиллы пакета в каталогах агента: `skills.<agents\|claude\|codex>.<project\|personal>` — набор, версия, совпадение текста с пакетом, перекрытие личной копией; `skills.installed` — у агента скиллов нет; `skills.claude.plugins` — плагины Claude Code с теми же скиллами; `skills.session` — всегда `–`: что загрузила сессия агента, CLI не видит |
| `render` | `render.plantuml` — крошечная C4-диаграмма движком сборки; `render.d2`, `render.mermaid` — если такие файлы есть в проекте; `render.full` — с `--full` |
| `project` | `project.config` — `.c4builder` найден и валиден; `project.complete` — сборка пройдёт без мастера; `project.paths` — `rootFolder` и пути плагинов существуют |
| `runtime` | `runtime.port` — порт (`-p`, иначе из файла состояния сервера, иначе `webPort`) свободен, на нём `site -w` (с адресом) или чужой процесс; `runtime.agent` — какой агент определён и включён ли агентский режим |

`c4builder doctor skills project` — только перечисленные группы; неизвестная группа — список групп и
код 2. Каталоги скиллов: под агентом — его и `.agents/skills`, без агента — все (Claude Code,
Codex, `.agents`).

| Флаг | Значение |
|---|---|
| `--json` | один JSON-объект в stdout: `version`, `channel`, `agent`, `checks` (`id`, `status`, `message`, `fix`, `askUser`, `details`), `summary`; id проверок между версиями не меняются |
| `-v, --verbose` | абсолютные пути и подробности (путь к java, файлы скилла, не совпавшие с пакетом, лог пробной сборки) |
| `--strict` | код 1 и при предупреждениях — для CI |
| `--full` | вдобавок к крошечной диаграмме — сборка шаблонного проекта (`new --name doctor -y`) во временном каталоге, который удаляется при любом исходе; без Java — `–` |
| `--offline` | ни одного сетевого запроса |

Коды возврата: 0 — ошибок нет (предупреждения допустимы), 1 — есть ошибка, с `--strict` — и
предупреждение, 2 — неизвестная группа. `–` на код не влияет.

Новую версию doctor проверяет сам — `npm view` с таймаутом 3 с; нет ответа — `–`, не ошибка.
`CI` и `NO_UPDATE_NOTIFIER` эту проверку не выключают: doctor запускают явно. Фоновой проверки и
строки о новой версии в конце у `doctor` нет.

Вывод без `-v` можно вставлять в issue: домашний каталог показан как `~`, пути внутри проекта —
относительно, значений переменных окружения нет — только факт, что переменная задана.

## Комментарии на сайте

В `c4builder site -w` у выделенного текста появляются кнопки — по одной на адресата:

- **Comment** — комментарий людям: строка в журнале ревью (ключ `comments`, см.
  [Журнал ревью](#журнал-ревью));
- **Tell agent** — замечание coding-агенту, в файлы не пишется (агентский режим, см.
  [Замечания агенту](#замечания-агенту)).

Без журнала и без агентского режима кнопок нет; без `-w` и на статическом хостинге — тоже.
Подписи кнопок меняет ключ `buttons`: подпись из него показывается как есть на любом языке
интерфейса.

```json
{ "buttons": { "agent": "Поправить", "comment": "Заметка" } }
```

Кнопки **Question** (вопрос в раздел `questionsHeading` исходного файла) больше нет: ключи
`questions` и `questionsHeading` игнорируются, комментарии людям оставляют в журнале ревью.

### Журнал ревью

Комментарий, который должен попасть не в сам документ, а в отдельный журнал ревью (у OpenSpec —
`review.md` change'а), добавляет кнопка **Comment**: выделите текст, нажмите её, напишите
комментарий и нажмите **Add comment** (`Ctrl+Enter`). Кнопка появляется, когда в `.c4builder` есть
ключ `comments`:

```json
{
  "comments": {
    "file": "review.md",
    "heading": "Замечания",
    "cells": ["", "{artifact} → {section}", "{text}", "{author}", "", ""],
    "author": ""
  }
}
```

- `file` — имя файла журнала (по умолчанию `review.md`): берётся ближайший от каталога исходника
  страницы вверх по дереву до корня проекта. Так комментарий со страницы дельты `specs/<area>/spec.md`
  попадает в `review.md` change'а. Файла нет — ошибка, журнал не создаётся.
- `heading` — раздел журнала (по умолчанию `Review`): строка или список вариантов, если шаблоны
  журнала различаются (`["Замечания", "Замечания к design"]`) — пишется в первый найденный в файле,
  нет ни одного — создаётся первый. Комментарий дописывается строкой таблицы, если раздел — таблица
  (с очередным номером, если первая колонка числовая), иначе пунктом списка.
- `cells` — ячейки строки таблицы с подстановками: `{comment}` — текст, `{quote}` — цитата (до 200
  символов), `{text}` — `{comment} — «{quote}»`, `{section}` — раздел страницы, `{artifact}` — имя
  исходника без расширения (`design`, `spec`; у `README.md` — имя папки), `{page}` — исходник
  относительно каталога журнала, `{author}`, `{date}` (ГГГГ-ММ-ДД), `{number}` — номер строки.
  Числовая первая колонка получает номер сама; лишние ячейки шаблона отбрасываются, недостающие —
  пустые. Без `cells` строка — `комментарий — «цитата» (§ раздел)` в колонке текста.
- `author` — автор; по умолчанию `git config user.name` того, кто запустил `site -w`.
- `enabled` — `false` выключает кнопку и маршруты журнала, не удаляя остальную настройку.

Прежнее имя ключа — `reviewLog` с теми же полями: он работает, пока в `.c4builder` нет `comments`
(при обоих действует `comments`). Его поле `label` подписывает кнопку, если не задан `buttons.comment`.
В `comments` поля `label` нет: сборка предупреждает о нём и подписывает кнопку только из `buttons.comment`.

Watch пересобирает сайт, страница перезагружается уже с комментарием. На странице самого журнала
(исходник страницы — `file`) у строк раздела `heading` есть кнопка «×» (видна при наведении): она
удаляет строку из файла, номера остальных не меняются. На странице, с которой сделан комментарий, его
цитата подсвечена жёлтым, номер над ней ведёт на строку журнала. Какие строки относятся к странице,
определяется по `cells`: ячейка с `{artifact}` или `{page}` сравнивается со страницей, цитата
берётся из `{quote}` или из хвоста `{text}`; без таких подстановок подсвечиваются все строки с цитатой.

Интерфейс страницы — на русском или английском, по языку браузера; закрепить язык можно ключом
`uiLanguage`. Здесь кнопки названы по-английски, в русском интерфейсе **Comment** — «Комментарий»,
**Add comment** — «Добавить комментарий», **Tell agent** — «Сказать агенту». Остальные подписи — на
странице [Агенты](08%20Агенты/08%20Агенты.md).

## Замечания агенту

Агентский режим `site -w` включается, если выполнено любое из условий:

- передан флаг `--agent`;
- задана переменная `C4BUILDER_AGENT` со значением не `0` (значение — имя агента в подсказке);
- есть переменная известного агента: `CLAUDECODE` (Claude Code), `CODEX_THREAD_ID` (Codex),
  `GEMINI_CLI`, `OPENCODE`, `COPILOT_CLI` или `AI_AGENT`;
- к серверу подключилась команда `c4builder feedback` — режим включается на лету, страница
  показывает кнопку **Tell agent** без перезагрузки.

`--no-agent` или `C4BUILDER_AGENT=0` выключают режим при любых остальных условиях; флаги сильнее
переменных. Запущенный в агентском режиме по флагу или переменной `site -w` печатает подсказку, как
получать замечания.

На странице у выделения кнопка **Tell agent** (с журналом рядом — **Comment**). Её поле ввода
отправляет замечание сразу (**Send now**) или откладывает его (**Add**), как в merge request GitLab:
когда есть отложенные замечания, основная кнопка и `Ctrl+Enter` — **Add**. Панель агента внизу
страницы показывает число отложенных замечаний и страниц (`To agent: 2 pending (1 page)`), адресата и
его состояние (`foo: listening ●` / `foo: reconnecting ○`, без агентов — `agent: not listening ○`) и
кнопки. Пока отложенных замечаний нет, кнопка одна — **Done — no changes**: правок нет, агенту уходит
пачка `approved` без замечаний. Когда они есть — **Send to agent** (с необязательным общим
комментарием), **Approve** (правок больше нет; отложенные замечания уходят вместе с ним) и **Discard**
(очистить отложенные, агенту ничего не уходит). Клик по счётчику раскрывает список с «×» у каждого
замечания. Отложенные замечания хранятся в `localStorage` браузера отдельно для каждого проекта и
адресата, переживают перезагрузку и закрытие вкладки, их цитаты подсвечены синим.

На одном `site -w` могут работать несколько агентов: каждый слушает под своим именем
(`--as <имя>`), и у сервера свой ящик на каждое имя. Когда адресатов больше одного, в панели
появляется выбор **Send to** со списком имён и их состоянием (`listening`, `reconnecting`, число
пачек в очереди). Выбор запоминается на вкладку и переживает перезагрузку, поэтому три вкладки могут
работать с тремя агентами. Пока вкладка не выбрала адресата, кнопки отправки недоступны. С одним
агентом выбора нет: он становится адресатом вкладки сам. Замечания, отложенные до появления агента,
переходят к первому адресату вкладки.

`c4builder feedback --wait --as <имя>` подключается к `site -w` на порту из `-p`, иначе из файла состояния
сервера, иначе `webPort`, ждёт
следующую пачку для `<имя>` без ограничения по времени, печатает её в stdout markdown-ом и
завершается с кодом 0. Если `<имя>` — id change'а на сайте (плагин `openspec`), команда перед
ожиданием печатает в stderr одну строку `Change page: http://localhost:<порт>/#/change/<имя>` —
ссылку на страницу change'а для человека; stdout остаётся только для пачки, нет такого change'а —
строки нет. Без `--wait` команда печатает пачку, если она уже в ящике, иначе ничего, и
сразу завершается. Без `--as` или с недопустимым именем — код 2 и сообщение `--as <name> is
required` с примером, к серверу команда не обращается. Нет сервера или режим выключен — код 1 и
сообщение с адресом сервера. Пачка, отправленная адресату, пока он не слушает (например, агент
правит файлы между пачками), ждёт в его ящике и уходит следующей команде с тем же именем; пачка,
отправленная, когда агентов ещё не было, — первой подключившейся команде. Страница сообщает
«в очереди у `<имя>`», а «доставлено `<имя>`» — только после выдачи. Пустой ящик, к которому
30 минут никто не подключался, пропадает из списка; ящик с пачками остаётся. Ящики живут в памяти
процесса `site -w`. Формат пачки и цикл агента — на странице
[Агенты](08%20Агенты/08%20Агенты.md).

## Как читается конфиг

`.c4builder` — JSON в папке проекта. Первая сборка задаёт недостающие ключи через мастер и
ставит `hasRun: true`; после этого `c4builder` собирает без вопросов. `new -y` сразу пишет
полный конфиг, поэтому мастера не будет вовсе.

Мастеру нужен терминал. Без него (CI, фоновый запуск, coding-агент) отсутствующий конфиг — ошибка
с кодом 1, файлы не создаются, а неполный останавливается на первом вопросе с
`aborted: the prompt was closed` и кодом 1. Закрытие мастера по `Ctrl+C` тоже даёт код 1.
`.c4builder`, который не разбирается как JSON, — ошибка с именем файла и причиной; файл остаётся
как есть.

Ключи проверяются схемой. Значение не того типа останавливает сборку с ошибкой, где назван
ключ, а `c4builder config` позволяет его исправить. Неизвестные ключи молча
отбрасываются — так старый c4builder не падает на конфиге от нового. Ключи функций, удалённых
из старых версий, дают предупреждение с их списком, сборка продолжается.

| `buttons` | — | свои подписи кнопок у выделения в `site -w`: `agent` (вместо **Tell agent**), `comment` (вместо **Comment**) — см. [Комментарии на сайте](#комментарии-на-сайте) |
| `comments` | — | журнал ревью для кнопки **Comment** в `site -w`: `enabled`, `file`, `heading`, `cells`, `author` (прежнее имя — `reviewLog`) — см. [Журнал ревью](#журнал-ревью) |
| `uiLanguage` | `auto` | язык интерфейса страницы `site -w`: `auto` (по браузеру), `en` или `ru` |
| `webFileName` | — | одно имя `.md` для всех страниц сайта вместо имени папки |
| `excludeSidebarFolderByPath` | — | список путей (от папки проекта, например `src/Архив`), скрытых из sidebar |
| `plugins` | `[]` | плагины сборки, см. [Плагины](06%20Плагины/06%20Плагины.md) |

Конфиг сайта этой документации — живой пример: `docs/ru/.c4builder` в репозитории.

## Свой шаблон docsify

`docsifyTemplate` указывает на ESM- или CommonJS-модуль, который экспортирует функцию.
Она получает объект настроек docsify (имя, sidebar, тема, поиск) и возвращает HTML для
`index.html`. Отправная точка — встроенный шаблон в `src/core/compose/docsify.template.ts`;
у этого сайта свой — `docs/docsify-template.mjs`.

Сворачивание sidebar (`sidebarCollapse`) в шаблоне подключать не нужно: его скрипт и стиль
сборка вставляет в готовый `index.html` пост-обработкой, как ассеты плагинов, а уровень
раскрытия приходит в объекте настроек ключом `sidebarDisplayLevel` — достаточно вставить
объект в `window.$docsify` целиком. Если шаблон уже подключает
`vendor/docsify-sidebar-collapse.min.js` сам, второй раз файл не добавляется.
