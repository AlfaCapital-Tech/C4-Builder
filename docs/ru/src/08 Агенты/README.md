# Агенты

C4-модель в текстовом виде агент правит так же уверенно, как код: `Person`, `System`,
`Container` и `Rel` в `.puml` — это готовая семантическая модель, а не картинка. Не хватает
ему обычно другого: быстрого и однозначного ответа «сломал или нет». c4builder даёт его
локально, без сети и без человека.

## Цикл правка → check → сборка

1. **Правка.** Агент меняет `.md` и `.puml`/`.d2` в `src/` — добавляет контейнер, связь,
   страницу.
2. **Проверка.** `c4builder check` на изменённых файлах:

   ```bash
   c4builder check "src/1 Internet Banking System/system.puml"
   ```

   Код выхода 0 — всё собирается. Код 1 — в выводе строка с файлом и номером строки:

   ```text
   ✗ src/1 Internet Banking System/system.puml: строка 12: Fatal parsing error
   ```

   Проверка идёт тем же движком и с теми же `!include`, что и сборка, и занимает секунды:
   агент исправляет ошибку и повторяет, пока не получит 0.
3. **Сборка.** `c4builder` собирает проект целиком; `c4builder --site -w` держит сайт
   открытым у человека и пересобирает его на каждое сохранение агента.

Полная сборка тоже завершается с кодом не 0, если не отрендерилась хотя бы одна диаграмма,
поэтому её можно ставить последним шагом агента или в CI.

## Почему офлайн-рендер важен для агентов

- **Нет сети — нет случайных отказов.** PlantUML-jar, C4-библиотека, шрифт и D2 лежат в
  пакете; сборка не зависит от plantuml.com, прокси и лимитов.
- **Один вход — один выход.** Вендорный шрифт и закреплённые версии движков дают
  одинаковые SVG на любой машине. Дифф в pull request показывает то, что агент изменил в
  модели, а не шум окружения.
- **Исходники не уходят наружу.** Архитектура часто содержит то, чему не место на чужом
  сервере; локальный рендер это исключает.

## Скиллы для агентов

c4builder поставляет [Agent Skills](https://agentskills.io) для Claude Code, Codex, Cursor и других
агентов, которые поддерживает утилита [`skills`](https://github.com/vercel-labs/skills). Скиллы
лежат в папке `skills/` репозитория (в npm-пакет не входят) и описывают последний стабильный
релиз, поэтому команды в них записаны флагами: `--new`, `--config`.

```bash
npx skills add AlfaCapital-Tech/C4-Builder/skills                    # оба скилла в текущий проект
npx skills add AlfaCapital-Tech/C4-Builder/skills --skill c4builder  # только один
```

`-g` ставит скиллы пользователю, а не в проект. Путь `/skills` в команде обязателен: без него
утилита подхватит ещё и служебные скиллы разработки самого c4builder из `.claude/skills/`.

| Скилл | Когда пригодится |
|---|---|
| `c4builder` | работа с проектом: раскладка `src/` и `.c4builder`, цикл правка → `c4builder check` → сборка, конвенции C4-PlantUML (stdlib-инклюды, общий `.iuml`, офлайн-рендер), D2, плагины `openspec` и `openapi`, `llms.txt` |
| `c4builder-setup` | установка и обновление (npm-каналы `latest` и `rc`, Docker-образ), Java или скачиваемая JRE, проверочная сборка шаблонного проекта |

## AGENTS.md в новом проекте

С версии 0.5.0 `c4builder --new` кладёт в проект `AGENTS.md`: команды сборки и проверки, порядок
работы, раскладку проекта, конвенции диаграмм и команду установки скиллов. Его читают Codex,
Cursor и Claude Code. Файл лежит рядом с `src/`, а не внутри, и в документацию не попадает.

## llms.txt: архитектура для чтения агентом

С `"generateLLMS": true` (с версии 0.5.0, нужен `generateWEB`) в корне сайта появляются два файла
по соглашению [llmstxt.org](https://llmstxt.org/):

- **`llms.txt`** — точка входа: имя проекта, краткое описание и плоский список страниц в порядке
  sidebar, вида `- [Система / Контейнер](Система/Контейнер/Контейнер.md)`. Папки из
  `excludeSidebarFolderByPath` в список не попадают, страницы плагинов (например, `openspec`)
  попадают. Ссылки — относительно корня сайта.
- **`llms-full.txt`** — полный текст всех страниц одним файлом, в том же порядке, что и единый
  markdown. Каждая диаграмма вставлена **исходником** в блоке `plantuml` или `d2`, а не картинкой —
  независимо от `diagramFormat`, `embedDiagram` и `includeLinkToDiagram`. Локальные `!include` и
  D2-импорты (вложенные тоже) приводятся один раз в приложении `## Included files` в конце;
  stdlib-инклюды `!include <C4/...>` и инклюды по URL остаются строками в исходнике.

Исходник полезнее картинки: текст C4-PlantUML (`Person`, `System`, `Rel`) — готовая модель, а SVG
по ссылке агенту ничего не даёт. Чтобы ответить на вопрос «от чего зависит сервис X», агенту
достаточно прочитать `llms-full.txt`, не обходя страницы.

Без сайта сборка печатает предупреждение и файлы не создаёт. В новых проектах ключ включён;
существующий `.c4builder` без ключа собирается как раньше — включите его через
`c4builder --config` или добавьте `"generateLLMS": true` в конфиг.

Файлы этого сайта:

| Оглавление | [ru/llms.txt](https://alfacapital-tech.github.io/C4-Builder/ru/llms.txt) | [en/llms.txt](https://alfacapital-tech.github.io/C4-Builder/en/llms.txt) |
| Полный текст | [ru/llms-full.txt](https://alfacapital-tech.github.io/C4-Builder/ru/llms-full.txt) | [en/llms-full.txt](https://alfacapital-tech.github.io/C4-Builder/en/llms-full.txt) |

## Подсказки для инструкций агента

В проекте, созданном до 0.5.0, `AGENTS.md` нет. Что стоит записать в `AGENTS.md` или `CLAUDE.md`
такого проекта:

- после правки диаграммы — `c4builder check <файл>`, исправлять до кода выхода 0;
- C4 подключать через stdlib (`!include <C4/C4_Container>`), общие стили — `!include ../styles.iuml`;
- новая страница — новая папка в `src/`, порядок — числовым префиксом;
- имена `.puml` и `.d2` в одной папке не должны совпадать без учёта расширения: выходной файл
  у них общий, и сборка остановится с ошибкой.

Плюс pre-commit-хук со страницы [Диаграммы](03%20Диаграммы/03%20Диаграммы.md): он не даст
закоммитить несобираемую диаграмму ни человеку, ни агенту.
