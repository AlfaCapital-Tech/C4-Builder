# diagram-rendering

## Purpose

Требования к рендеру PlantUML-диаграмм при сборке: работа без внешнего graphviz (Java-движок раскладки Smetana), прямой вызов `java` с вендорным JAR в pipe-режиме и детерминированные метрики текста за счёт вендорного шрифта.
## Requirements
### Requirement: Диаграммы рендерятся без внешнего graphviz
Сборка SHALL рендерить PlantUML-диаграммы с использованием встроенного в PlantUML Java-движка раскладки (Smetana, `-Playout=smetana`) и MUST NOT требовать наличия внешнего graphviz/dot. Отсутствие или неработоспособность `dot` в системе MUST NOT приводить к ошибке рендера.

#### Scenario: Рендер при отсутствующем graphviz
- **WHEN** выполняется сборка, а исполняемый файл `dot` в системе недоступен
- **THEN** все диаграммы (C4 context/container/component/deployment/dynamic, class, sequence) успешно рендерятся в SVG, а кириллица в выходе сохраняется

#### Scenario: dot не вызывается
- **WHEN** запущен рендер диаграмм
- **THEN** процесс сборки не порождает вызовов внешнего `dot`

### Requirement: Рендер вызывает java напрямую
Сборка SHALL запускать PlantUML прямым вызовом `java` с вендорным JAR, без посреднической библиотеки `node-plantuml`. Источником данных MUST быть stdin/stdout (pipe-режим), чтобы имя выходного файла определялось c4builder по имени `.puml`-файла, а не по имени диаграммы из директивы `@startuml`.

#### Scenario: Имя выходного файла независимо от @startuml
- **WHEN** рендерится диаграмма, у которой в `@startuml <name>` задано имя, отличное от имени файла
- **THEN** выходной файл именуется по имени `.puml`-файла (как прежде), а не по `<name>`

#### Scenario: Локальные и stdlib-инклюды резолвятся
- **WHEN** рендерится диаграмма с `!include <C4/...>` (stdlib) и `!include ../styles.iuml` (локальный файл)
- **THEN** оба вида инклюдов резолвятся, диаграмма собирается корректно

### Requirement: Детерминированные метрики текста через вендорный шрифт
Ширина текста в SVG зависит от метрик шрифта, поэтому сборка SHALL использовать шрифт, поставляемый в составе репозитория (`vendor/fonts/`), и задавать его как шрифт диаграмм по умолчанию. Шрифт MUST физически предоставляться JVM (а не только задаваться по имени), чтобы исключить молчаливый откат на системный шрифт.

#### Scenario: Рендер использует вендорный шрифт
- **WHEN** выполняется сборка на машине, где заданный шрифт не установлен системно
- **THEN** рендер использует шрифт из `vendor/fonts/`, а не системный fallback

#### Scenario: Повторяемость метрик
- **WHEN** одна и та же диаграмма рендерится дважды на одной машине
- **THEN** геометрия выходного SVG (координаты и `textLength`) байт-в-байт идентична

### Requirement: Второй бэкенд рендера выбирается по расширению
Сборка SHALL поддерживать `.d2`-диаграммы наравне с `.puml` и выбирать движок
рендера по расширению файла: `.puml` — PlantUML, `.d2` — D2. Добавление D2 MUST NOT
менять поведение существующих `.puml`-проектов; выходной файл диаграммы именуется по
имени исходного файла, формат — SVG.

#### Scenario: Смешанное дерево .puml и .d2
- **WHEN** в дереве проекта присутствуют и `.puml`, и `.d2` файлы
- **THEN** `.puml` рендерятся PlantUML, `.d2` рендерятся D2, оба дают SVG рядом с
  прочими выходами, ссылки в markdown работают для обоих

#### Scenario: Проект только из .puml не затронут
- **WHEN** в проекте нет ни одного `.d2`-файла
- **THEN** сборка и её выход идентичны прежнему поведению, а зависимость D2 не
  загружается

### Requirement: Импорты D2 резолвятся через виртуальную файловую систему
D2-рендерер SHALL собирать граф импортов (`@`/`...@`) исходного `.d2`-файла и
передавать движку виртуальную файловую систему (`compile({ fs, inputPath })`), чтобы
переиспользуемые стили и определения из отдельных `.d2`-файлов применялись. Тот же
граф импортов MUST учитываться в чексумме кэша диаграмм: правка импортируемого файла
инвалидирует зависимые диаграммы.

#### Scenario: Общие стили через импорт
- **WHEN** `.d2`-диаграмма импортирует общий файл (`...@c4lib`) с classes/vars
- **THEN** импортируемые стили применяются в выходном SVG

#### Scenario: Правка импортируемого файла инвалидирует кэш
- **WHEN** изменён импортируемый `.d2`-файл, а сама диаграмма — нет
- **THEN** при следующей сборке зависимая диаграмма перерисовывается, а не берётся из кэша

### Requirement: Зависимость D2 опциональна и загружается лениво
Пакет движка D2 SHALL быть опциональной зависимостью и загружаться только при
наличии в проекте хотя бы одного `.d2`-файла. При наличии `.d2` и отсутствии пакета
сборка MUST завершаться понятной ошибкой с указанием, как установить зависимость.
После завершения рендера D2 ресурсы движка (webworker) MUST освобождаться, чтобы
процесс сборки корректно завершался.

#### Scenario: .d2 без установленного движка
- **WHEN** в проекте есть `.d2`, но пакет движка D2 не установлен
- **THEN** сборка падает с понятным сообщением и подсказкой установки, а не с
  невнятной ошибкой модуля

#### Scenario: Процесс завершается после сборки
- **WHEN** сборка с `.d2`-диаграммами завершена
- **THEN** CLI-процесс завершается и не остаётся висеть из-за незакрытого воркера
