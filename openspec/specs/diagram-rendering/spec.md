# diagram-rendering

## Purpose

Требования к рендеру PlantUML-диаграмм при сборке: работа без внешнего graphviz (Java-движок раскладки Smetana), прямой вызов `java` с вендорным JAR в pipe-режиме и детерминированные метрики текста за счёт вендорного шрифта.

## Requirements

### Requirement: Диаграммы рендерятся без внешнего graphviz
Сборка SHALL рендерить PlantUML-диаграммы с использованием встроенного в PlantUML Java-движка раскладки (Smetana, `-Playout=smetana`) и MUST NOT требовать наличия внешнего graphviz/dot. Отсутствие или неработоспособность `dot` в системе MUST NOT приводить к ошибке рендера.

#### Scenario: Рендер при отсутствующем graphviz
- **WHEN** выполняется сборка, а исполняемый файл `dot` в системе недоступен
- **THEN** все диаграммы (C4 context/container/component/deployment/dynamic, class, sequence) успешно рендерятся в SVG, а кириллица в выходе сохраняется

#### Scenario: dot не вызывается
- **WHEN** запущен рендер диаграмм
- **THEN** процесс сборки не порождает вызовов внешнего `dot`

### Requirement: Рендер вызывает java напрямую
Сборка SHALL запускать PlantUML прямым вызовом Java с вендорным JAR, без посреднической
библиотеки `node-plantuml`. Исполняемый файл Java MUST определяться резолвером JRE
(см. capability `jre-resolution`: системная → кеш → публичный Adoptium), а не браться
безусловно как голая `java` из `PATH`. Источником данных MUST быть stdin/stdout
(pipe-режим), чтобы имя выходного файла определялось c4builder по имени `.puml`-файла,
а не по имени диаграммы из директивы `@startuml`.

#### Scenario: Имя выходного файла независимо от @startuml
- **WHEN** рендерится диаграмма, у которой в `@startuml <name>` задано имя, отличное от имени файла
- **THEN** выходной файл именуется по имени `.puml`-файла (как прежде), а не по `<name>`

#### Scenario: Локальные и stdlib-инклюды резолвятся
- **WHEN** рендерится диаграмма с `!include <C4/...>` (stdlib) и `!include ../styles.iuml` (локальный файл)
- **THEN** оба вида инклюдов резолвятся, диаграмма собирается корректно

#### Scenario: Java берётся из резолвера, а не голой из PATH
- **WHEN** годной системной java на `PATH` нет, но JRE доступен через кеш или скачивание
- **THEN** рендер использует резолвнутый бинарь Java и успешно рендерит диаграммы, а не
  падает с «java не найдена»

### Requirement: Детерминированные метрики текста через вендорный шрифт
Ширина текста в SVG зависит от метрик шрифта, поэтому сборка SHALL по умолчанию использовать шрифт Nimbus Sans, поставляемый в составе репозитория (`vendor/fonts/`), и задавать его как шрифт диаграмм по умолчанию. Шрифт MUST физически предоставляться JVM (а не только задаваться по имени), чтобы исключить молчаливый откат на системный шрифт. Пин действует, когда режим системных шрифтов выключен (`useSystemFonts=false`, значение по умолчанию).

#### Scenario: Рендер использует вендорный шрифт
- **WHEN** выполняется сборка на машине, где заданный шрифт не установлен системно
- **THEN** рендер использует шрифт из `vendor/fonts/`, а не системный fallback

#### Scenario: Повторяемость метрик
- **WHEN** одна и та же диаграмма рендерится дважды на одной машине
- **THEN** геометрия выходного SVG (координаты и `textLength`) байт-в-байт идентична

### Requirement: Режим системных шрифтов
Сборка SHALL поддерживать режим системных шрифтов: ключ `useSystemFonts`
(boolean, по умолчанию `false`) в `.c4builder` и CLI-флаг `--system-fonts`,
разово включающий режим независимо от конфига (флаг сильнее ключа). При
включённом режиме рендер MUST NOT передавать JVM шрифтовые аргументы
(`-Dsun.java2d.fontpath`, `-SdefaultFontName`, `-SCircledCharacterFontName`) —
PlantUML использует системный шрифт, как до вендорного пина. Ключ кеша рендера
MUST различать режимы шрифта: результат одного режима MUST NOT отдаваться из
кеша в другом. Вывод в этом режиме машинозависим — это ожидаемо и
детерминизм для него NOT гарантируется.

#### Scenario: Флаг включает системные шрифты поверх конфига
- **WHEN** в `.c4builder` ключ `useSystemFonts` отсутствует или равен `false`, но сборка запущена с `--system-fonts`
- **THEN** JVM запускается без шрифтовых аргументов, растеризатор использует системные шрифты

#### Scenario: Отсутствие ключа — прежнее поведение
- **WHEN** `.c4builder` не содержит ключ `useSystemFonts` (например, конфиг репо arch)
- **THEN** рендер идёт с вендорным шрифтом, поведение сборки не отличается от режима по умолчанию

#### Scenario: Кеш не смешивает режимы
- **WHEN** одна и та же диаграмма рендерится сначала в режиме по умолчанию, затем с `--system-fonts`
- **THEN** второй рендер не берёт результат первого из кеша (и наоборот)

#### Scenario: Golden-контур не зависит от режима
- **WHEN** выполняются golden-тесты
- **THEN** они рендерят вендорным шрифтом; режим системных шрифтов покрыт проверкой аргументов рендера, а не пиксельной сверкой

### Requirement: Второй бэкенд рендера выбирается по расширению
Сборка SHALL поддерживать `.d2`-, `.bpmn`-, `.mmd`- и wireflow-диаграммы наравне с `.puml` и
выбирать движок рендера по расширению файла:
- `.puml` — PlantUML;
- `.d2` — D2;
- `.bpmn` — BPMN-движок (см. capability `bpmn-diagrams`);
- `.mmd` — mermaid-движок (см. capability `mermaid-diagrams`);
- `.wireflow.json` и имя `wireflow.json` — wireflow-движок (см. capability `wireflow-diagrams`);
  расширение определяется по полному суффиксу, прочие `.json` диаграммами не являются.

Добавление движков MUST NOT менять поведение существующих `.puml`-проектов. Выходной файл
диаграммы именуется по имени исходного файла без расширения движка (для wireflow — без
`.wireflow.json`). Формат рендера всех движков — SVG. При `DIAGRAM_FORMAT=png` SVG
растеризуется в PNG отдельной стадией (см. требование о PNG-выводе).

#### Scenario: Смешанное дерево .puml и .d2
- **WHEN** в дереве проекта присутствуют и `.puml`, и `.d2` файлы
- **THEN** `.puml` рендерятся PlantUML, `.d2` рендерятся D2, при формате по умолчанию
  (svg) оба дают SVG рядом с прочими выходами, ссылки в markdown работают для обоих

#### Scenario: BPMN рядом с другими движками
- **WHEN** в дереве проекта присутствуют `.puml`, `.d2` и `.bpmn` файлы
- **THEN** каждый файл рендерится своим движком, `.bpmn` даёт SVG (или PNG при
  `DIAGRAM_FORMAT=png`) с именем по исходному файлу, ссылки в markdown работают для всех

#### Scenario: Mermaid рядом с другими движками
- **WHEN** в дереве проекта присутствуют `.puml`, `.d2`, `.bpmn` и `.mmd` файлы
- **THEN** каждый файл рендерится своим движком, `.mmd` даёт SVG (или PNG при
  `DIAGRAM_FORMAT=png`) с именем по исходному файлу, ссылки в markdown работают для всех

#### Scenario: Wireflow рядом с другими движками
- **WHEN** в дереве проекта присутствуют `.puml`, `.mmd` и `checkout.wireflow.json`
- **THEN** каждый файл рендерится своим движком, `checkout.wireflow.json` даёт `checkout.svg`
  (или `checkout.png` при `DIAGRAM_FORMAT=png`), ссылка `![](checkout.wireflow.json)` в
  markdown заменяется картинкой

#### Scenario: Проект только из .puml не затронут
- **WHEN** в проекте нет ни одного `.d2`-, `.bpmn`-, `.mmd`- и wireflow-файла и ни одного блока
  ```` ```mermaid ````
- **THEN** сборка и её выход идентичны прежнему поведению, а зависимости D2, BPMN и mermaid
  не загружаются
