# release-publishing

## Purpose

Требования к публикации npm-пакета через GitHub Actions: триггер строго по push git-тега версии, выбор dist-tag по семантике версии (пререлиз → `rc`, стабильная → `latest`), гейт синхронизации тега и версии из `package.json`, идемпотентность повторного запуска и сохранение provenance/trusted publishing (OIDC) без долгоживущих npm-токенов.

## Requirements

### Requirement: Публикация запускается только push-ем git-тега версии

Публикация пакета в npm SHALL выполняться GitHub Actions workflow, триггер которого — исключительно push git-тега вида `v*` (например `v0.3.0-rc.1`, `v0.3.0`), плюс ручной `workflow_dispatch`. Workflow MUST NOT публиковать пакет по событию `push` в `master` или по мержу ветки. Обычные коммиты и мержи в `master` MUST NOT приводить к публикации.

#### Scenario: Push тега версии
- **WHEN** в репозиторий пушится git-тег `v0.3.0-rc.1`
- **THEN** workflow публикации запускается и выполняет шаг публикации пакета

#### Scenario: Push/мерж в master
- **WHEN** выполнен push или мерж ветки в `master` без нового тега `v*`
- **THEN** workflow публикации не запускается и пакет не публикуется

### Requirement: Dist-tag выбирается по семантике версии

Workflow MUST определять dist-tag по версии из `package.json`: если версия — пререлиз (содержит `-`, например `0.3.0-rc.1`), публикация выполняется командой `npm publish --tag rc`; если версия стабильная (без `-`, например `0.3.0`), публикация выполняется в dist-tag `latest`. Это гарантирует, что пререлизы не смещают `latest` и не попадают в `npm install` без явного запроса.

#### Scenario: Публикация пререлиза
- **WHEN** публикуется версия `0.3.0-rc.1`
- **THEN** пакет публикуется под dist-tag `rc`, а `latest` остаётся на прежней стабильной версии

#### Scenario: Публикация стабильной версии
- **WHEN** публикуется версия `0.3.0` без суффикса пререлиза
- **THEN** пакет публикуется в dist-tag `latest`

#### Scenario: Установка релиз-кандидата
- **WHEN** пользователь выполняет `npm install @alfacapital-tech/c4builder@rc`
- **THEN** ставится последняя версия под тегом `rc`, тогда как `npm install` без тега продолжает ставить `latest`

### Requirement: Гейт синхронизации тега и версии

Перед публикацией workflow MUST проверять, что строка git-тега совпадает с версией из `package.json` в форме `v<version>`. При несовпадении workflow MUST завершаться с ошибкой и НЕ публиковать пакет — это защита от рассинхрона, при котором `npm publish` опубликовал бы версию из `package.json`, не совпадающую с намерением тега.

#### Scenario: Тег совпадает с версией
- **WHEN** тег `v0.3.0-rc.1`, а версия в `package.json` — `0.3.0-rc.1`
- **THEN** гейт проходит и workflow переходит к публикации

#### Scenario: Тег не совпадает с версией
- **WHEN** тег `v0.3.0-rc.1`, а версия в `package.json` — `0.2.25`
- **THEN** workflow завершается с ненулевым кодом и ничего не публикует

### Requirement: Идемпотентность публикации

Workflow MUST пропускать шаг публикации, если версия из `package.json` уже опубликована в npm-реестре. Повторный запуск workflow для уже опубликованной версии MUST завершаться успешно без попытки повторной публикации (без ошибки конфликта).

#### Scenario: Версия уже опубликована
- **WHEN** workflow запущен для версии, которая уже присутствует в реестре
- **THEN** шаг публикации пропускается, workflow завершается успешно

#### Scenario: Новая версия
- **WHEN** workflow запущен для версии, которой ещё нет в реестре
- **THEN** пакет публикуется под соответствующим dist-tag

### Requirement: Сохранение provenance и trusted publishing

Workflow MUST публиковать пакет с `--provenance` через OIDC trusted publishing (`permissions: id-token: write`), без хранения долгоживущих npm-токенов в секретах репозитория. Модель аутентификации MUST оставаться неизменной при переходе на тег-драйв.

#### Scenario: Публикация с provenance
- **WHEN** выполняется шаг публикации пакета
- **THEN** пакет публикуется с флагом `--provenance` и аутентификацией через OIDC, без использования статического npm-токена
