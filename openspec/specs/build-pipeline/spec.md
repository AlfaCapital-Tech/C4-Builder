# build-pipeline Specification

## Purpose
Как устроен и собирается код CLI: TypeScript/ESM под `strict`, компиляция `tsc` в `dist/` без бандлера, запуск из собранного `dist/`, сохранение наблюдаемого поведения при порте и пофазная модульность ядра сборки (scan → render → compose).

## Requirements

### Requirement: Исходники на TypeScript и ESM

Исходный код CLI SHALL быть написан на TypeScript в модульной системе ESM.
Все модули под `src/` MUST иметь расширение `.ts`; `package.json` MUST
декларировать `"type": "module"`; модули MUST использовать `import`/`export`
(не `require`/`module.exports`) и лежать под `src/`, организованные по доменам
(`cli/`, `core/`, `config/`, `util/`). Компиляция MUST проходить в режиме
`strict` без ошибок.

#### Scenario: Модульный формат исходников
- **WHEN** просматривается любой модуль под `src/`
- **THEN** это `.ts`-файл с ESM-синтаксисом (`import`/`export`), а `package.json` содержит `"type": "module"`

#### Scenario: Строгая компиляция
- **WHEN** выполняется `npm run build`
- **THEN** `tsc` компилирует все модули `src/` в режиме `strict` без ошибок

#### Scenario: Ресурсы вне компиляции доступны из собранного кода
- **WHEN** собранный модуль обращается к вендорным ресурсам (`vendor/`) или шаблону (`template/`)
- **THEN** путь резолвится к корню пакета через `import.meta.url`, а не к каталогу внутри `dist/`, и рендер/скаффолд находят JAR, шрифты и шаблон

### Requirement: Компиляция tsc → dist/ без бандлера

Проект SHALL компилироваться `tsc` в каталог `dist/` без бандлера. `tsconfig.json`
MUST задавать `module`/`moduleResolution` `nodenext`, `outDir: dist`, `rootDir: src`.
Относительные импорты в исходниках MUST указывать расширение `.ts`
(`allowImportingTsExtensions`), а `tsc` MUST переписывать их в `.js` в эмите
(`rewriteRelativeImportExtensions`). `allowJs` MUST быть выключен: `.js`-модули
под `src/` не допускаются.

#### Scenario: Сборка порождает dist
- **WHEN** выполняется `npm run build`
- **THEN** `tsc` компилирует `src/**` в `dist/**` с расширениями `.js`, без бандлинга

#### Scenario: Расширения импортов переписываются
- **WHEN** исходный модуль содержит `import './render/diagram.ts'`
- **THEN** в соответствующем файле `dist/` импорт эмитится как `import './render/diagram.js'`

#### Scenario: Смесь .ts/.js запрещена
- **WHEN** под `src/` появляется `.js`-модуль
- **THEN** он не входит в компиляцию (`allowJs: false`) и сборка не может на него ссылаться

### Requirement: CLI запускается из собранного dist/

Опубликованный и локально собранный CLI SHALL исполняться из `dist/`. Поля `bin`
и `main` в `package.json` MUST указывать на `dist/index.js`; точка входа MUST
сохранять shebang `#!/usr/bin/env node`.

#### Scenario: Запуск собранного CLI
- **WHEN** после `npm run build` выполняется `node dist/index.js --help`
- **THEN** CLI выводит справку (эквивалентно запуску до порта)

#### Scenario: bin установленного пакета указывает на dist
- **WHEN** пакет установлен и вызвана команда `c4builder`
- **THEN** запускается `dist/index.js`

### Requirement: Порт сохраняет наблюдаемое поведение

Переход на TypeScript/ESM MUST NOT менять наблюдаемое поведение CLI: вывод сборки
(сайт/markdown, диаграммы), формат конфига `.c4builder` и совместимость с
конфигом потребителя MUST оставаться прежними. Golden-набор MUST проходить без
регенерации эталонов.

#### Scenario: Golden-паритет
- **WHEN** golden-набор прогоняется на собранном из `dist/` CLI
- **THEN** результат совпадает с эталонами без их обновления

### Requirement: Пофазная модульность ядра сборки

Ядро сборки SHALL быть организовано по фазам: скан дерева исходников
(`core/scan/`), рендер диаграмм (`core/render/`) и компоуз выводов
(`core/compose/`) MUST жить в отдельных модулях со своими экспортируемыми
типами границ. `core/build.ts` SHALL содержать только оркестрацию
(последовательность фаз, бэкап/восстановление выходного каталога, прогресс)
и MUST NOT содержать логику самих фаз.

#### Scenario: Фазы в отдельных модулях
- **WHEN** просматривается `src/core/`
- **THEN** построение дерева, рендер диаграмм и генерация markdown/сайта находятся в модулях `scan/`, `render/`, `compose/` соответственно, а не в `build.ts`

#### Scenario: Оркестратор без логики фаз
- **WHEN** просматривается `src/core/build.ts`
- **THEN** он импортирует фазы как модули и не содержит реализации скана, рендера или компоуза

#### Scenario: Дробление не меняет поведение
- **WHEN** golden-набор прогоняется после выделения фаз
- **THEN** результат совпадает с эталонами без их регенерации

### Requirement: Прогресс сборки вне терминала
Когда stdout — не терминал (лог фонового процесса, CI), сборка MUST NOT печатать
обновляемый счётчик прогресса с `\r`; вместо него — одна итоговая строка на фазу
(`processed <N> images`, `processed <N> files`). В терминале поведение не меняется.

#### Scenario: Лог фонового процесса
- **WHEN** `c4builder --site -w` запущен с перенаправлением вывода в файл и рендерит 179 диаграмм
- **THEN** в файле нет символов `\r`, а подсказка агентского режима стоит отдельной строкой после `processed 179 images`

### Requirement: Ошибки диаграмм в сборке — в формате check
Строгая сборка (`c4builder`, `--site` без `-w`) SHALL печатать каждую упавшую диаграмму одной
строкой в stderr в том же формате, что `c4builder check` для того же файла:
`✗ <file>: line <N>: <message>` (путь от текущего каталога, строка — от начала файла, с 1) или
`✗ <file>: <message>`, если позиции нет. Вывод движка (Java-стек PlantUML) и стек Node MUST NOT
попадать в вывод по умолчанию.

#### Scenario: Синтаксическая ошибка PlantUML
- **WHEN** `src/dangling.puml` содержит незакрытую скобку в строке 4 и запускается сборка
- **THEN** stderr содержит `✗ src/dangling.puml: line 4: Fatal parsing error` — ту же строку, что печатает `c4builder check src/dangling.puml`, — и не содержит `java.lang.` и `at render (`

#### Scenario: Ошибка без позиции
- **WHEN** PlantUML завершился с ошибкой без блока позиции (сбой движка)
- **THEN** печатается одна строка `✗ <file>: <первая строка сообщения>` с подсказкой о `--verbose`

### Requirement: Сборка сообщает обо всех сломанных диаграммах
Строгая сборка SHALL дорендерить все диаграммы и перечислить все упавшие (в порядке обхода
исходников), а не остановиться на первой. Ошибка окружения — нет java, сбой render-worker — MUST
останавливать рендер сразу и печататься один раз, а не по строке на диаграмму.

#### Scenario: Две сломанные диаграммы
- **WHEN** в проекте сломаны `a.puml` и `b.d2`, остальные корректны
- **THEN** напечатаны обе строки `✗ …a.puml: …` и `✗ …b.d2: …`, корректные диаграммы отрендерены

#### Scenario: Нет java
- **WHEN** java недоступна и автозагрузка JRE не удалась, в проекте 100 диаграмм PlantUML
- **THEN** сообщение о java печатается один раз, сборка завершается с кодом 1

### Requirement: Завершение сборки при ошибке диаграмм
После списка ошибок сборка SHALL печатать `build aborted — …` (при наличии бэкапа прошлого выхода,
как раньше) и завершаться с кодом 1 без необработанного исключения.

#### Scenario: Код выхода и хвост вывода
- **WHEN** сборка с одной сломанной диаграммой запущена с выводом не в терминал
- **THEN** код выхода 1, последняя строка stderr/stdout — не стек Node (`Node.js v…`), строки `✗` идут до `build aborted`

### Requirement: Подробности ошибки — по запросу
С флагом `-v, --verbose` или при `DEBUG`, содержащем `c4builder` (список через запятую, `*` — всё),
сборка SHALL дополнительно печатать полный вывод движка и стек для каждой ошибки диаграммы.
Без них подробности MUST NOT печататься.

#### Scenario: Полный стек по флагу
- **WHEN** сборка со сломанной диаграммой запущена с `--verbose`
- **THEN** после строки `✗ …` печатается вывод PlantUML со стеком Java, код выхода по-прежнему 1

#### Scenario: Через переменную окружения
- **WHEN** сборка запущена с `DEBUG=c4builder`
- **THEN** вывод такой же, как с `--verbose`

### Requirement: Короткий формат ошибок в мягких путях рендера
Предупреждение о мягкой диаграмме (блок в markdown, диаграмма плагина) и сообщение о заглушке
с ошибкой в dev-сервере (`site -w`) SHALL использовать тот же короткий текст ошибки
(`line <N>: <message>`), что и строгая сборка, без вывода движка.

#### Scenario: Битая диаграмма в site -w
- **WHEN** во время `c4builder --site -w` сохранена `.puml` с синтаксической ошибкой
- **THEN** в лог печатается одна строка `✗ <file>: line <N>: <message>`, на сайте — заглушка с ошибкой, сервер работает

### Requirement: Баннер только в терминале
ASCII-баннер и строка-слоган SHALL печататься, только если stdout — терминал; очистка экрана
перед мастером — тоже. Вне терминала (CI, лог агента, перенаправление в файл) их MUST NOT быть.

#### Scenario: Сборка в CI
- **WHEN** `c4builder` запущен с stdout в файл
- **THEN** в файле нет ASCII-баннера и управляющих последовательностей очистки экрана

#### Scenario: Сборка в терминале
- **WHEN** `c4builder` запущен в интерактивном терминале
- **THEN** баннер печатается, как раньше
