# Design

## Context

Мотивация — см. proposal.md. Исследование (2026-10, прототипы на процессах ПИФ: 5 дорожек +
black-box пул, 23 узла; 3 пула, 37 узлов, 4 message flow) дало такую картину.

**Раскладка с горизонтальными дорожками — самое слабое звено экосистемы.**
- `bpmn-auto-layout` 1.x (bpmn-io) раскладывает только первого участника, пулы и дорожки
  игнорирует.
- 2.0.0-alpha.0–2 (июль 2026, тег `next`) — новый семантический layered-движок: пулы,
  вложенные горизонтальные дорожки, message flow, boundary events, `warnings`, детерминированный
  вывод (проверено побайтно). API — `layoutProcess(xml) → { xml, warnings }`.
  - Открытые дефекты: плотные циклы (#150), наложения рёбер (#147/#148), TypeError на
    нестандартной модели (#155).
- Альтернативы:
  - `bpmn-elk-layout` снят с npm 29.09.2026 — ребрендинг в `tramito-layout` (Apache-2.0,
    движок коммерческого сервиса, один автор), на тестах раскладывает хуже;
  - `bpmn-auto-layout-extended` — форк одного автора;
  - elkjs, maxGraph и Java-раскладчики горизонтальные дорожки не умеют.

**Рендер.**
- Все известные docs-as-code инструменты (Kroki, asciidoctor-diagram, MkDocs-плагины)
  рендерят BPMN в headless Chromium, нам это запрещено.
- `bpmn-js` Viewer работает под jsdom без правки исходников:
  - текст меряется только через `canvas.getContext('2d').measureText`
    (`diagram-js/lib/util/Text.js`);
  - `getBBox` нужен только `saveSVG` для viewBox;
  - нужны заглушки SVGMatrix/SVGTransformList.
  - Прототип на Nimbus Sans дал побайтно одинаковые SVG и PNG в трёх прогонах.
- Лицензия bpmn-js — MIT + условие о водяном знаке. Для экспортированного SVG оно не действует:
  ответ мейнтейнера bpmn-io (forum.bpmn.io, 19.08.2026, «Our license doesn't require the
  watermark on the exported diagrams»), после него Kroki закрыл yuzutech/kroki#2140.
- Особенности `saveSVG`:
  - id маркеров случайные (`marker-<random>`);
  - `url('#…')` пишется в кавычках, а resvg такие ссылки игнорирует, и стрелки пропадают.

**Источник и валидация.**
- По исследованиям (arXiv 2507.11356, 2509.24592) BPMN XML без DI на 64–70% короче полного без
  потери качества генерации. Сильные модели правят XML почти так же точно, как JSON.
- Бенчмарков по дорожкам нет — качество проверяем своим eval.
- Цикл исправления по ошибкам валидатора сводит сбои к нулю (ProMoAI, в среднем 1,35 итерации).
- `bpmnlint` 11.x (MIT, чистый Node) линтует семантическую модель и сообщает id элемента. Но он,
  как и раскладчик, опирается на `incoming`/`outgoing`: если агент пишет только
  `sourceRef`/`targetRef`, получается каскад ложных ошибок (57 на тестовой модели).

**Устройство c4builder.**
- Движки — реестр `DIAGRAM_ENGINES` (`src/core/scan/tree.ts`).
- Рендер и кэш — `src/core/render/diagrams.ts`. Ключ кэша — префикс движка с версиями, как
  у D2.
- Образец ленивой опциональной зависимости — `d2renderer.ts`.
- `check` — таблица `CHECKERS` в `src/cli/commands/check.ts`.
- PNG — растеризация SVG через resvg (обычная зависимость).
- Плагины добавлять движки не умеют, это сознательная граница контракта (`plugins/types.ts`).

## Goals / Non-Goals

**Goals:**
- Агент пишет `.bpmn` без координат и за один цикл `check` получает либо картинку, либо точные
  ошибки с id элементов.
- Привычная BPMN-нотация с горизонтальными пулами и дорожками в сайте, md и PNG.
- Детерминизм и офлайн на уровне PlantUML/D2: golden-тесты, без браузера и сети.

**Non-Goals:**
- Ручная доводка раскладки (учёт DI из источника), выдача `.bpmn` с DI для внешних редакторов.
- Интерактивный просмотрщик (zoom/pan) на сайте, fence ```` ```bpmn ```` в артефактах OpenSpec.
- Исполняемый BPMN, расширения Camunda/Flowable, проектный `.bpmnlintrc`.
- Свой раскладчик или свой рендерер.

## Decisions

1. **Источник — стандартный BPMN 2.0 XML, а не свой DSL.**
   - Модели знают стандарт.
   - Файл открывается любым BPMN-инструментом.
   - Валидатор и раскладчик работают с XML напрямую.
   - *Альтернатива* — компактный YAML/JSON с компиляцией в XML (Stieges/bpmn-generator,
     BPMN Assistant): примерно на 75% меньше выходных токенов, но это свой язык на поддержке,
     которого модели не знают. Выигрыш заметен только на слабых моделях.

2. **DI из источника всегда отбрасывается, раскладка всегда автоматическая.**
   - Нет проблемы устаревшего DI: агент добавил узел в файл с ручными координатами, а фигуры
     у узла нет.
   - Нет двух режимов поведения.
   - *Альтернатива* «полный DI — берём, неполный — раскладываем заново» добавляется позже без
     ломки, если раскладчик где-то не справится. Сейчас у этого нет потребителя.

3. **Конвейер одного файла** (модуль `bpmnrenderer.ts`, общий для сборки и `check`):
   1. **Разбор и нормализация** через `bpmn-moddle`:
      - `incoming`/`outgoing` восстанавливаются из `sourceRef`/`targetRef`;
      - `definitions.diagrams` очищается;
      - висячие ссылки и ошибки импорта превращаются в ошибку «файл: id: причина».
   2. **Валидация** через `bpmnlint` по нормализованной модели (решение 4). Ошибки
      прерывают конвейер, предупреждения уходят в лог.
   3. **Раскладка:** `layoutProcess(xml)` из `bpmn-auto-layout`. Исключение превращается в
      ошибку «файл: раскладка не удалась: <сообщение>», `warnings` — в предупреждения.
   4. **Рендер:**
      - `bpmn-js` Viewer в изолированном окне jsdom: production-бандл
        `bpmn-viewer.production.min.js` выполняется в окне, глобальные объекты процесса Node не
        трогаются;
      - `importXML` → `saveSVG`.
   5. **Постобработка SVG:**
      - viewBox считается из DI через `elementRegistry` (без `getBBox`), с отступом;
      - `marker-<random>` переименовываются в `marker-<n>` по порядку появления;
      - кавычки в `url('#…')` снимаются.
   6. **PNG** — штатная растеризация (`pngraster.ts`).

   Окно jsdom одно на процесс сборки, закрывается в `teardown` (как воркер D2), чтобы CLI
   завершался.

4. **Набор правил валидации фиксирован и встроен в c4builder.**
   - Берётся `bpmnlint:recommended` без `no-bpmndi`: DI в источнике не нужен.
   - Плюс плагин c4builder:
     - `lane-membership` (error): если у процесса есть дорожки, каждый flow node ровно в
       одной;
     - `sequence-flow-in-pool` (error, с подсказкой «используйте message flow»);
     - `message-flow-between-pools` (error);
     - `gateway-flow-labels` (warning): у исходящих потоков XOR/inclusive-шлюза с несколькими
       выходами есть подписи.
   - Правила грузятся статическим резолвером, без поиска пакетов `bpmnlint-plugin-*` в
     `node_modules` проекта.
   - *Альтернатива* — проектный `.bpmnlintrc`: гибче, но ломает одинаковость «что проверил
     агент = что проверит CI» и добавляет конфиг-поверхность. Добавим, если команды попросят.

5. **Метрики текста — вендорный Nimbus Sans через resvg, который уже в зависимостях.**
   - Полифил `measureText` в окне jsdom считает ширину строки рендером текста в resvg
     (`getBBox`, ~0,17 мс на замер) или по advance-ширинам шрифта.
   - `textRenderer` настраивается на `Nimbus Sans`.
   - Режим системных шрифтов на BPMN не влияет (как и на D2): детерминизм важнее.
   - В браузере без Nimbus SVG показывается метрически совместимым Helvetica/Arial.
   - *Альтернатива* `opentype.js` — ещё одна зависимость ради того, что resvg уже умеет.
     Расхождение между ними на прототипе меньше 1 px.

6. **Зависимости — `optionalDependencies` с точным пином, ленивая загрузка.**
   - Пакеты: `bpmn-js`, `bpmn-moddle`, `bpmnlint`, `bpmn-auto-layout@2.0.0-alpha.N` (точная
     последняя alpha на момент реализации), `jsdom@29`.
   - jsdom 29 (`^20.19 || ^22.13 || >=24`) покрывает границу `>=22.17` из change'а
     `node-22`. jsdom 30 требует `^22.22.2 || ^24.15`: переход на него — вместе с будущим
     подъёмом `engines`.
   - Загрузка — при первом `.bpmn`. Нет пакетов — ошибка с подсказкой
     `npm i -g @alfacapital-tech/c4builder` без `--omit=optional` (как у D2).
   - Ключ кэша: `bpmn\0<версии bpmn-js, bpmn-auto-layout, bpmnlint>\0fmt=<svg|png>` + содержимое.

7. **Реестр и вывод.**
   - `{ ext: '.bpmn', engine: 'bpmn', remoteRender: false }` в `DIAGRAM_ENGINES`.
   - Выход `<имя>.svg`/`.png` по имени файла; ссылки в md — штатные.
   - `check`: `'.bpmn'` в `CHECKERS` и в тексте подсказки по расширениям. Сообщение об ошибке
     валидации — `✗ <файл>: <id> [<правило>] <описание>`, по строке на нарушение.
   - В `llms-full.txt` (change `llms-txt`) исходник вставляется fence'ом с языком `xml`.
     Локальных зависимостей у `.bpmn` нет, приложение include-файлов не пополняется.

8. **Пример в шаблоне — `template/src/5 BPMN Example/`.** Тема продолжает демо «Internet
   Banking System»: «Открытие счёта».
   - Пулы: «Банк» с дорожками «Клиент», «Фронт-офис», «Бэк-офис» и внешний «Бюро кредитных
     историй» (black-box).
   - Есть XOR с подписанными ветками, граничный таймер на задаче, message flow.
   - md-страница объясняет, что пишется только семантика.
   - Пример же — golden-fixture и образец для скилла. Внутренних процессов компании в
     публичном репозитории нет.

## Risks / Trade-offs

- **Раскладчик в alpha:** API и координаты меняются между версиями, есть известные дефекты.
  - Точный пин; golden ловит любой сдвиг.
  - Исключение превращается в понятную ошибку с путём файла.
  - Найденные на eval дефекты — upstream issues.
  - Запасные пути: вендорить зафиксированную версию (MIT) или перейти на
    `bpmn-auto-layout-extended` / `tramito-layout`, интерфейс которых тот же «XML → XML с DI».
- **Полифилы jsdom ломаются при обновлении bpmn-js** → точный пин; обновление — отдельным PR с
  переснятием golden. Крайний вариант — свой рендерер по DI (1–1,5 тыс. строк), сейчас не
  делаем.
- **Обойти неудачную раскладку конкретной диаграммы нечем:** DI игнорируется. Можно
  переструктурировать модель (вынести подпроцесс, разбить на обзор и детализацию — это пишем в
  скилл) или дождаться режима учёта DI (Non-Goal сейчас).
- **Качество моделей по дорожкам не измерено** → eval на 2–3 реальных процессах ЭДО до
  объявления фичи готовой (tasks). Процессы и картинки остаются вне публичного репозитория,
  в репозиторий попадают только выводы и issues.
- **Установка `npm i -g` тяжелеет** (jsdom, bpmn-js) для всех, включая проекты без BPMN →
  прецедент D2 (~60 МБ) уже принят; `--omit=optional` оставляет только ядро.
- **Широкие диаграммы на 40+ узлов плохо читаются картинкой на сайте** → в скилле: обзорный
  процесс плюс детализация подпроцессов. Интерактивный просмотрщик — следующий шаг, если
  понадобится.

## Migration Plan

Аддитивно: проекты без `.bpmn` не меняются, golden-эталоны существующих вариантов меняются
только добавлением BPMN-раздела шаблона. Порядок: после `node-22`; задачи по скиллу и сайту —
после вмерживания `agent-skills` и `docs-site`. Откат — revert PR (раздел шаблона, движок и
зависимости уходят вместе).
