# Design: golden-test-ci

## Context

c4builder — CLI на CommonJS (~2300 строк), тестов нет, CI только публикует. Конфиг проекта читается из файла `.c4builder` в cwd (Configstore с явным `configPath`), кэш чексумм диаграмм — из `.c4builder.cache`; при наличии конфига CLI работает неинтерактивно. PlantUML рендерится через node-plantuml, JAR подменяется на вендорный через `PLANTUML_HOME` (выбор — опцией `PLANTUML_VERSION`). Главный потребитель — репо `arch`: C4-PlantUML stdlib, локальные `.iuml`, кириллица, `diagramFormat=svg`, `generateLocalImages=true`.

Место в цепочке: сразу после `template-offline` (шаблон переведён на stdlib-инклюды, содержит `.iuml` и кириллицу, собирается офлайн — и используется здесь как fixture), до remove-pdf → ts-migration → рендер-фич. Задача — построить страховочную сеть до любых переделок кода.

## Goals / Non-Goals

**Goals:**
- Зафиксировать текущее поведение сборки (site / md / complete-md + SVG) как исполняемый контракт.
- Тесты запускаются одной командой локально и на каждый PR в GitHub Actions.
- Fixture воспроизводит ключевые особенности `arch` (через демо-шаблон: stdlib, `.iuml`, кириллица).

**Non-Goals:**
- Юнит-тесты отдельных функций (придут вместе с TS-портом).
- Покрытие PDF-выходов (PDF удаляется следующим change'ом).
- Покрытие интерактивного режима (inquirer), пути `c4builder new` (интерактивен насквозь; неинтерактивные флаги — будущий change `new-noninteractive`) и `c4builder site` (dev-сервер).
- Привязка publish-workflow к зелёному CI (отдельный шаг после стабилизации).
- Изменение продуктового кода.

## Decisions

1. **Тест-раннер — vitest** (не `node:test`): встроенные снапшоты и диффы, watch-режим, нативная поддержка будущего TS без перенастройки. Alternative: `node:test` без зависимостей — отвергнут из-за слабой эргономики диффов больших деревьев.

2. **E2E через реальный запуск CLI**, не программный вызов `build()`: тест копирует fixture во временную директорию, кладёт готовый `.c4builder` и спавнит `node <repo>/index.js` с `cwd=tmp`. Так покрываются `cli.js`, `getOptions`, миграция кэша — весь неинтерактивный путь целиком. Программный вызов оставляем юнит-тестам будущего.

3. **Fixture — демо-шаблон `template/src`**, отдельный «мини-arch» не заводим. Тест-хелпер копирует шаблон в tmp и кладёт готовый `.c4builder` (`diagramFormat=svg`, `generateLocalImages=true`, `PLANTUML_VERSION` пинован на вендорный 1.2025.2, выходы site/md/complete-md, PDF выключен) — неинтерактивный эквивалент `c4builder new`. После `template-offline` шаблон покрывает stdlib-инклюды, `.iuml` и кириллицу, рендер офлайн и детерминирован по версии PlantUML. Правка шаблона в будущем = осознанная регенерация эталона в том же PR: дифф эталона наглядно показывает эффект правки. Alternative — замороженная копия шаблона в `test/fixtures/`: развязывает демо и тесты, но дублирует контент и позволяет шаблону незаметно сломаться; отвергнут.

4. **Golden-хранение и сравнение**: эталонное дерево выходов коммитится в `test/golden/`. Сравнение — (а) идентичность списка файлов, (б) байтовое равенство содержимого после нормализации: из SVG вырезаются XML-комментарии (метаданные/версия PlantUML), все файлы приводятся к LF. Обновление эталона только явно: `UPDATE_GOLDEN=1 npm run test:golden` (скрипт `test:golden:update`).

5. **Кэш-инвариант вторым тест-кейсом**: повторная сборка в той же tmp-директории (с уже наполненным `.c4builder.cache`) обязана дать выход, идентичный первому прогону, — фиксируем корректность checksum-кэша.

6. **CI**: workflow `ci.yml` на `pull_request` + `push` в master; runner пинован `ubuntu-24.04` (стабильная версия graphviz); матрица Node 22/24; `actions/setup-java` (Temurin 21) + `apt-get install graphviz`; `npm ci --ignore-scripts`, `npm test`; `concurrency` с cancel-in-progress.

## Risks / Trade-offs

- [Расхождение layout из-за версии graphviz локально vs CI] → CI объявляется источником истины для эталона; runner пинован; при локальном расхождении — регенерация эталона артефактом из CI или запуск в docker-образе проекта. Риск исчезает после перехода на Smetana (change `plantuml-java-direct`).
- [Недетерминизм внутри SVG (метаданные, порядок атрибутов)] → нормализация комментариев; если вскроется большее — расширяем нормализатор, это часть данного change.
- [JVM-старт и рендер удлиняют CI] → fixture маленький (3–4 диаграммы), ожидаемо < 1 мин на job.
- [Тест зависит от вендорного JAR в репо] → JAR уже в git (vendor/), удаление старых JAR — забота будущего change'а `vendor-cleanup`, здесь пин на существующий.
- [Связность template ↔ golden: правка демо ломает эталон] → это осознанно: несовпадение при неумышленной правке — ровно то, что тест должен ловить; умышленная правка сопровождается `UPDATE_GOLDEN=1` в том же PR.
