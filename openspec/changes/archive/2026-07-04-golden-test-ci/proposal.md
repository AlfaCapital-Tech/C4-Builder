# Golden-тест и CI-проверки

## Why

В проекте ноль тестов, а CI только публикует пакет — регресс заметить нечем. Впереди цепочка крупных изменений (удаление PDF, порт на TypeScript, замена PlantUML-рендера, resvg, D2): без страховочной сети каждое из них непроверяемо. Golden-тест фиксирует текущее поведение как контракт **до** любых переделок — прежде всего совместимость с главным потребителем, репо `arch` (108 .puml, C4-PlantUML stdlib, локальные .iuml-инклюды, кириллица, diagramFormat=svg).

## What Changes

- Fixture — сам демо-шаблон `template/src` (после change'а `template-offline` он содержит stdlib-инклюды, локальный `.iuml`, кириллицу и собирается офлайн). Отдельный рукотворный fixture не заводится; тест-хелпер копирует шаблон во временную директорию и кладёт готовый `.c4builder` (`diagramFormat=svg`, `generateLocalImages=true`) — неинтерактивный эквивалент `c4builder new`.
- Golden e2e-тест: прогон текущего CLI по fixture, сравнение полного дерева выходных файлов с закоммиченным эталоном (после нормализации недетерминизма: комментарии PlantUML-версии в SVG и т.п.).
- Тест-раннер vitest (работает с текущим CommonJS, останется после порта на TS); npm-скрипты `test` / `test:golden`.
- Новый workflow `.github/workflows/ci.yml`: прогон тестов на PR и push, матрица Node 22/24, setup-java (Temurin) для реального PlantUML-рендера.
- PDF-выходы golden-тестом сознательно **не** покрываются: PDF недетерминирован и удаляется следующим change'ом (`remove-pdf-output`).
- Путь `c4builder new` не покрывается: он насквозь интерактивен (inquirer без флагов); неинтерактивный режим и e2e «new → build» — будущий change (`new-noninteractive`).
- Продуктовый код не меняется (кроме случая, если golden вскроет недетерминизм, который надо будет стабилизировать).
- Предусловие: change `template-offline` применён (шаблон собирается офлайн).

## Capabilities

### New Capabilities
- `regression-testing`: golden-тест фиксирует выходы сборки (site/md/complete-md + SVG-диаграммы) на эталонном fixture-проекте и падает при любом расхождении.
- `ci-validation`: GitHub Actions прогоняет тесты на каждый PR и push в master; публикация возможна только при зелёных проверках.

### Modified Capabilities

_нет — существующих спеков ещё нет._

## Impact

- Новые каталоги: `test/` (тесты и эталонные выходы; fixture — существующий `template/src`).
- Новые dev-зависимости: `vitest`.
- `package.json`: секция `scripts` (сейчас пустая).
- Новый `.github/workflows/ci.yml`; существующие `publish.yml` / `docker-publish.yml` не трогаем (связка «публикация после зелёного CI» — отдельным шагом, чтобы не блокировать релизы до стабилизации тестов).
- Поведение CLI не меняется.
