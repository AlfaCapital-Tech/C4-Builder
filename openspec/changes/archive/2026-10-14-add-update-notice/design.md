## Context

Мотивация — в `proposal.md`, требования — в `specs/cli-update`. Что важно для подхода:

- Основную установку (`npm i -g`) делают в том числе из корпсети: реестр там бывает
  внутренним, выход наружу — через прокси, а `fetch`/`https` в Node 22.17 переменные
  `HTTPS_PROXY` по умолчанию не учитывают. `npm` берёт реестр, прокси и сертификаты из
  npmrc сам, и это тот же путь, по которому пользователь будет ставить обновление.
- Сборки в CI (GitLab у arch, GitHub Actions здесь) часто идут без интернета и обязаны
  завершаться за то же время, что и сейчас.
- `src/cli/dispatch.ts`: после `program.parse` команды `--version`/`--help` уже вышли
  (это делает commander), дальше идёт маршрутизация по `cmd`. `src/cli/commands/site.ts`
  в режиме `-w` пропускает каждую отдаваемую HTML-страницу через `inject()`, туда и
  встаёт плашка.
- `src/util/paths.ts` даёт `PACKAGE_ROOT` и `packageJson` (сейчас типизирован только
  `version`).
- Тесты спавнят собранный CLI с наследованием `process.env`.

## Goals / Non-Goals

**Goals:**
- Минимум кода: один новый модуль, без новых зависимостей и без отдельного
  скрипта-воркера.
- Ни одного сценария, в котором сеть, её отсутствие или зависший `npm` задерживают
  запуск или завершение CLI.

**Non-Goals:**
- Тихая автоустановка обновлений.
- Минимальная версия CLI в `.c4builder`.
- Плашка в `c4builder site` без `-w` (статический сервер без `inject()`).
- Уведомление в терминале для `-w`/`site -w`, остановленных Ctrl+C: процесс гибнет по
  SIGINT без события `exit`, а человек в этом режиме видит плашку.
- Показ списка изменений новой версии.

## Decisions

### D1. Проверка — отсоединённый `npm view`, stdout которого направлен прямо в файл кэша

```
startUpdateCheck()                      (main process, ~1 ms)
  |  gated? (CI / NO_UPDATE_NOTIFIER / C4BUILDER_DOCKER / cmd=update) --> return
  |  mtime(cache) < 24h ago ?                                         --> return
  |  fd = open(cache, 'w');  futimes(fd, now)   <-- attempt time
  |  spawn npm view <pkg> dist-tags --json --fetch-retries=0 --fetch-timeout=5000
  |        { detached: true, stdio: ['ignore', fd, 'ignore'], windowsHide: true }
  |  child.on('error', noop); child.unref(); close(fd)
  v
main continues and exits without waiting; npm writes {"latest":..,"rc":..} itself
```

- Кэш — `${XDG_CONFIG_HOME:-~/.config}/c4builder/dist-tags.json`: содержимое — ответ
  npm как есть, mtime — время последней попытки. Ни отдельного поля `lastCheck`, ни
  `configstore`.
- `futimes` обязателен: `open(..., 'w')` на уже пустом файле (прошлая попытка без сети)
  на Linux не обновляет mtime, и тогда без сети `npm` запускался бы на каждом старте.
- `stdio: 'ignore'` + `detached` + `unref`, а не `execFile` + `unref`: у `execFile`
  pipe'ы stdout/stderr ребёнка держат event loop родителя до выхода ребёнка. Без сети
  это и есть зависание при выходе на всё время таймаутов npm.
- `--fetch-retries=0 --fetch-timeout=5000`: без них npm в сети, молча отбрасывающей
  пакеты, висит минутами (повторы с паузами до 60 с). Пользователю это не мешает, но
  отсоединённые процессы не должны копиться.
- `child.on('error')` обязателен: без обработчика отсутствие `npm` в `PATH` (ENOENT)
  роняет CLI необработанным `error`.
- Windows: `npm` — это `npm.cmd`, а Node ≥ 20.12 запускает `.cmd` только через shell,
  поэтому `shell: process.platform === 'win32'`. Аргументы фиксированные, инъекции нет.

Альтернативы:
- пакет `update-notifier` — тянет boxen и прочие зависимости, реестр резолвит сам, без
  прокси из npmrc;
- `fetch` в процессе — без прокси и держит процесс открытым;
- воркер-скрипт, пишущий кэш атомарно, — лишний файл ради сохранения старого
  результата при неудачной попытке. Потеря знания о версии на сутки без сети приемлема.

### D2. Отключение — три переменные, одна из них ставится образом

`CI` (ставят GitLab CI, GitHub Actions и большинство CI), `NO_UPDATE_NOTIFIER` (общая
конвенция с `update-notifier`) и `C4BUILDER_DOCKER=1`, которую `Dockerfile` задаёт через
`ENV`. Одна переменная образа служит и отключением, и признаком Docker для команды
`update`. Детект по `/.dockerenv` отвергнут: его нет в podman/k8s. Переменная к тому же
наследуется образами, собранными на нашем.

### D3. Уведомление — `process.once('exit')`, регистрируется при старте

Там же, где запускается проверка, читается кэш. Если обновление доступно, вешается
обработчик `exit`, который пишет строку в `process.stderr`. Так покрываются все пути
выхода, включая `process.exit(1)` при ошибках, и маршрутизацию команд трогать не нужно.
Запись в stderr при выходе синхронна для TTY, файлов и pipe'ов на Linux/macOS. На
Windows pipe асинхронный, и строка может потеряться — это допустимо.

### D4. Сравнение версий — своя функция на ~10 строк

`compareVersions(a, b)`: ядро `x.y.z` сравнивается численно; стабильная версия старше
пререлиза того же ядра; пререлизы сравниваются по точечным сегментам, числовые —
численно. `newestVersion(current, tags)` возвращает `latest`, а для пререлиза — бо́льшую из
`latest` и `rc`. Зависимость `semver` ради двух функций не добавляем. Битый или пустой
кэш означает «нет данных», без исключений.
Формат ответа `npm view … dist-tags --json` зависит от версии npm: npm ≤ 11 отдаёт объект,
npm 12 — массив из одного объекта; разбор принимает оба.

### D5. Плашка — в существующем `inject()` `site.ts`, кэш перечитывается на каждую страницу

`inject()` добавляет перед `</body>` фиксированный блок (правый нижний угол) на
английском: версии и `c4builder update`, плюс кнопка закрытия с флагом в `sessionStorage`
(в `try/catch`, как у скролла livereload). Кэш читается синхронно на каждую HTML-страницу:
это маленький файл и dev-сервер, зато результат фоновой проверки, запущенной этим же
`site -w`, появляется на следующей перезагрузке без перезапуска. SSE-событие не нужно:
ребилд и так перезагружает страницу. Признаки отключения (D2) скрывают и плашку.

### D6. `c4builder update` — в том же модуле, без чтения конфига

Маршрутизируется в `dispatch.ts` рядом с `jre`/`check`, до создания `Configstore`,
поэтому файлов в cwd не создаёт. Порядок действий:
1. `C4BUILDER_DOCKER` → печатает `docker pull ghcr.io/alfacapital-tech/c4builder:latest`, код 1.
2. `npm view <pkg> dist-tags --json` синхронно, с таймаутом. Ошибка → сообщение, код 1.
3. Обновления нет → `c4builder <v> is up to date`, код 0.
4. Если `realpath(PACKAGE_ROOT)` лежит внутри `realpath(npm root -g)`, выполняется
   `npm install -g <pkg>@<new>` с `stdio: 'inherit'`, код возврата — код npm. Иначе
   печатаются `npm i -D <pkg>@<new>` и `npx <pkg>@<new>`, код 1.

Ставится точная версия, а не `@latest`, потому что для пререлиз-канала новейшей может
оказаться `latest` (сейчас `rc` отстал от него). Имя пакета берётся из `package.json`
(тип `packageJson` расширяется полем `name`).

### D7. Модуль и тесты

Весь код — в новом `src/cli/update.ts` (`startUpdateCheck`, `pendingUpdate`,
`compareVersions`, `newestVersion`, `cmdUpdate`). Изменения в `dispatch.ts`, `site.ts`,
`paths.ts` и `Dockerfile` — по несколько строк.

- `vitest.config.mjs` → `test.env.NO_UPDATE_NOTIFIER = '1'`: ни один существующий спавн
  CLI не запускает настоящий `npm` и не пишет в настоящий `~/.config`.
- Новые тесты переопределяют env ребёнка явно: снимают `NO_UPDATE_NOTIFIER` и `CI`
  (GitHub Actions ставит `CI=true`), задают временный `XDG_CONFIG_HOME` и `PATH` с
  фейковым `npm`-скриптом, который пишет фиксированный JSON, спит или пишет маркер
  вызова. Тесты с фейковым `npm` — только на POSIX (`skipIf(win32)`).

## Risks / Trade-offs

- [Внутренний реестр отстаёт от npmjs или не проксирует пакет] → уведомление придёт
  позже или не придёт. Зато оно никогда не предложит версию, которую из этого реестра
  нельзя поставить.
- [Без сети неудачная попытка обнуляет кэш] → сутки без уведомления. Без сети обновиться
  всё равно нельзя.
- [Гонка: CLI читает кэш, пока npm в него пишет] → пустой или неполный JSON трактуется
  как «нет данных» (D4).
- [Отсоединённый `npm` остаётся жить после CLI] → ограничен таймаутом 5 с без повторов,
  не чаще раза в сутки.
- [Строка уведомления в stderr ломает чей-то разбор stderr] → в CI её нет (D2), для
  остальных случаев есть `NO_UPDATE_NOTIFIER=1`.
- [Агент сам запускает `c4builder update`] → скилл и `AGENTS.md` прямо запрещают делать
  это без просьбы пользователя.

## Migration Plan

Миграции нет: при первом запуске нужного каталога и кэша ещё нет, проверка их создаёт.
Откат — релиз без модуля; оставшийся файл `~/.config/c4builder/dist-tags.json` ни на
что не влияет.
