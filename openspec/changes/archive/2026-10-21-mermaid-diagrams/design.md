# Design

## Context

Сейчас три движка рендерятся при сборке:
- PlantUML — java и Smetana;
- D2 — WASM;
- BPMN — bpmn-js в окне jsdom, метрики текста через resvg по вендорному Nimbus Sans.

Fenced-блоки обрабатывает общий экстрактор `createFenceExtractor`
(`src/core/scan/fences.ts`). Он вырезает блок, кладёт его в диаграммы страницы с флагом
`soft` и ставит на его место `![name](name.ext)`. Языки экстрактора задаются отдельно:
- страницы проекта (`tree.ts`) — только `plantuml`;
- плагин openspec (`FENCE_LANGS`) — `plantuml`, `puml`, `d2`.

Движок диаграммы выбирается по расширению через `DIAGRAM_ENGINES`. Это касается и
диаграмм, которые порождают плагины.

Мотивация и рамки — в `proposal.md`, поведение — в `specs/mermaid-diagrams`.

Перед этим дизайном был спайк (explore-сессия 2026-10-21). Mermaid 12.2 работал в jsdom с
полифилом `getBBox` через resvg. Корректно рендерились flowchart с subgraph, sequence, state,
ER, class, gantt и pie, на одну диаграмму уходило 60–400 мс.

## Goals / Non-Goals

**Goals:**
- Mermaid — четвёртый движок того же уровня, что и остальные: тот же конвейер (кэш, `soft`,
  PNG, llms, `check`), без новых механизмов сборки.
- Узнаваемый вид mermaid, близкий к GitLab: тот же движок, классический стиль.
- Минимальный вес: один пакет около 2,7 МБ без транзитивных зависимостей. jsdom и resvg уже
  есть.

**Non-Goals:**
- `mindmap`, `architecture`, KaTeX — их нет в tiny-сборке. Полный `mermaid` (~200 МБ
  установки) ради них не тянем.
- Тёмная тема, `look: neo`/`handDrawn`, пользовательские `%%{init}%%`-темы сверх того, что
  mermaid применяет сам.
- Интерактивность: клики, tooltips, ссылки из узлов. Картинка статична, как у остальных
  движков.
- Пиксельная идентичность с GitLab. Шрифт другой (вендорный), метрики считаются по нему.

## Decisions

### 1. Движок — `@mermaid-js/tiny` в jsdom, а не браузер, beautiful-mermaid или mermaid-cli

| Вариант | Почему нет |
|---|---|
| Клиентский mermaid (vendored, плагин docsify) | Ломает концепт сборки. Нет кэша, `check`, PNG и картинок в md/llms. Недетерминирован. |
| `beautiful-mermaid` (чистый TS) | 6 типов, свой визуальный стиль. Ширины текста — эвристика под Inter. В SVG есть `@import` Google Fonts, `var()` и `color-mix()`, которые resvg не понимает. |
| `@mermaid-js/mermaid-cli` | Puppeteer и Chromium: сотни МБ, сеть при установке, тяжёлый docker. |
| Полный пакет `mermaid` | Около 199 МБ `node_modules` ради `mindmap` и `architecture`. Tiny рендерит то же самое. |

Tiny — официальная однофайловая IIFE-сборка mermaid той же версии. Она публикуется в npm
синхронно с `mermaid`. Пиним точную версию в `optionalDependencies`.

### 2. Исполнение внутри окна jsdom через `vm.runInContext`

Бандл выполняется в VM-контексте окна (`dom.getInternalVMContext()`). Глобальные объекты
процесса Node не трогаются, как у bpmn-js. `window.eval` не подходит: бандл начинается с
`"use strict"`, и в strict-eval его `var __esbuild_esm_mermaid_nm` не попадает в глобальный
объект. Скрипт через `vm` такой проблемы не имеет (проверено спайком).

Окно своё, не общее с BPMN. Движки независимы: у каждого свои полифилы, ленивая загрузка и
teardown. Общий модуль окна на два потребителя не окупается. Общее — только измерение через
resvg (см. решение 3).

### 3. Геометрия — `getBBox` через resvg

Mermaid задаёт размеры узлов по `getBBox()` подписей и групп, а viewBox — по `getBBox()`
корневого svg. В jsdom геометрии нет. Полифил устроен так:
- `SVGElement.prototype.getBBox` сериализует поддерево элемента без собственного
  `transform` в отдельный svg и отдаёт его resvg;
- resvg считает `getBBox()` с вендорным шрифтом, `loadSystemFonts: false`;
- `getComputedTextLength` — ширина того же bbox.

Это тот же приём, что у BPMN (`inkWidth`), только для произвольного поддерева, а не для
строки.

Тонкость: CSS mermaid (`#id{font-size:14px}`, классы) в изолированное поддерево не
попадает, а `getComputedStyle` jsdom к SVG его не применяет. Поэтому `text-anchor`, кегль,
жирность и baseline берутся мини-каскадом: inline-стиль, правила `<style>` диаграммы по
`matches()` и специфичности, атрибут, наследование от предков.

Второе (найдено сверкой с headless Chrome): resvg отдаёт bbox чернил, а браузер — advance-
ширину и em-box по ascent/descent шрифта, округлённым до пикселя. От этой высоты mermaid
центрирует подписи — отсюда съезжали текст в цилиндре и подпись пунктирной стрелки. Поэтому
`<text>` раскладывается эмуляцией (строки по `x`/`y`/`dy`, `text-anchor`, `central`/`middle`,
advance через resvg), а в поддереве заменяется прямоугольником своей раскладки; остальную
геометрию считает resvg. Подписи state выровнены влево и в Chrome — это поведение mermaid
при `htmlLabels: false`. Размеры обязательных типов совпадают с Chrome в пределах 1 px.

Пределы (не входят в обязательные типы): C4-диаграммы mermaid раскладываются иначе, чем в
браузере; у treemap другие отступы.

Результаты округляются, как `textWidth` у BPMN: f32-шум resvg между платформами иначе
просачивается в координаты.

### 4. Конфигурация mermaid фиксирована

```js
{
  startOnLoad: false,
  securityLevel: 'strict',
  look: 'classic',
  theme: 'default',
  fontFamily: 'Nimbus Sans',
  htmlLabels: false,
  flowchart: { htmlLabels: false },
  deterministicIds: true,
  gantt: { useWidth: 800 },
}
```

- `htmlLabels: false`: подписи — SVG `<text>`, а не `foreignObject`. resvg не рендерит
  `foreignObject`, а его геометрию в jsdom не измерить.
- `look: 'classic'`: в 12.x вид по умолчанию `neo` с фильтром `feDropShadow`. jsdom
  сериализует его как `fedropshadow`, resvg считает фильтр невалидным и не рисует узел
  целиком. Классический вид фильтров не использует. Постобработка дополнительно удаляет
  любые `filter=`/`<filter>`, если они всё же появятся (через `%%{init}%%`).
- `gantt.useWidth`: gantt берёт ширину контейнера (`getBoundingClientRect`), в jsdom она 0.
- Пользовательский `%%{init: …}%%` в источнике mermaid применяет сам. Ключи, которые ломают
  офлайн-рендер (`look`, `htmlLabels`, `securityLevel`, `fontFamily`), закреплены через
  `secure` в `initialize`.

### 5. Детерминизм — seed `Math.random` и нормализация id

Спайк нашёл два источника недетерминизма:
- счётчики id растут между рендерами в одном окне (sequence, class);
- `Math.random` в кривых связей ER.

Решение:
- на время каждого `render` `window.Math.random` заменяется PRNG с фиксированным seed (от
  хэша источника), после рендера восстанавливается;
- `render` получает id от хэша содержимого;
- постобработка переписывает внутренние id (`id=`, `url(#…)`, `href="#…"`) в порядке
  появления в документ-локальные (`m0`, `m1`, …), как в BPMN §3.5.

Рендеры строго последовательные: глобальный конфиг mermaid и подменённый `Math.random` на
параллельность не рассчитаны.

### 6. Fence-экстрактор и реестр движков

- `ENGINE_EXT`: `mermaid → .mmd`.
- `DIAGRAM_ENGINES`: `{ ext: '.mmd', engine: 'mermaid', remoteRender: false }`.
- Страницы проекта: экстрактор получает языки `['plantuml', 'mermaid']`.
- Плагин openspec: в `FENCE_LANGS` добавляется `mermaid`. Диаграммы плагинов выбирают
  движок по расширению и проходят тот же путь.

У `mermaid` нет «исходникового» синонима, как `puml` для PlantUML. Показать код mermaid можно
блоком с другим языком (`text`). Отдельный язык заводить не будем, пока его не попросят.

### 7. Ошибки, `check`, неподдерживаемые типы

- Ошибка разбора mermaid содержит `Parse error on line N:`. Номер строки извлекается в
  формат `check` (`✗ file: line N: msg`) и в сообщение сборки.
- Перед рендером тип определяется по первой значимой строке (после `%%`-директив и
  frontmatter). Для `mindmap`/`architecture*` выдаётся ошибка
  `unsupported mermaid diagram type 'mindmap'`. Без этого tiny отвечает невнятным
  `No diagram type detected`.
- Для `.mmd` ошибка жёсткая, для блоков — `soft`: заглушка и предупреждение. Это общий путь
  `diagrams.ts`.
- Если пакет tiny не установлен — сообщение с подсказкой
  `npm i -g @alfacapital-tech/c4builder` без `--omit=optional`, по образцу BPMN.

### 8. Кэш и llms

- Ключ кэша: `mermaid\0<версия @mermaid-js/tiny>\0fmt=<format>` плюс содержимое, как у BPMN.
- `llms-full.txt`: `FENCE_LANG['.mmd'] = 'mermaid'`. Блок из страницы возвращается в llms
  исходником (как `plantuml`).

## Risks / Trade-offs

- **Точность полифила `getBBox`.** Вид может отличаться от браузера на краевых случаях
  (длинные подписи, markdown-строки в узлах, `<br>`). Митигация: golden на flowchart и
  sequence, точечная подгонка, явный Non-Goal пиксельной идентичности.
- **Upstream меняет внутренности mermaid** (новые вызовы DOM-API, смена дефолтов) при
  обновлении tiny. Митигация: точный пин; golden ловит сдвиг; апгрейд — отдельный PR с
  переснятием эталонов.
- **Производительность.** resvg-вызов на каждый `getBBox` (50–90 на диаграмму). Для типичных
  проектов это сотни миллисекунд, кэш снимает повторы. Если станет узким местом — мемоизация
  по сериализованному поддереву.
- **Изменение `--md` для существующих пользователей.** Блок ```` ```mermaid ```` в md-выходе
  становится картинкой, а GitLab раньше рисовал его сам. Решение осознанное (единообразие),
  фиксируется в CHANGELOG.
- **Tiny «не для npm»** по README пакета. Пакет публикуется в npm каждым релизом mermaid, а
  исполняем мы ровно IIFE-файл, как в браузере. Если публикацию прекратят, перейдём на
  vendored-копию того же файла.

## Migration Plan

Флагов и миграций нет. Проекты без mermaid не меняются. В проектах с ```` ```mermaid ````
блоки становятся картинками после обновления. Откат — предыдущая версия c4builder.
