# Design

## Context

`check.ts` проверяет файлы по очереди. Ошибку каждого движка он превращает в строки
`✗ <file>: <problem>`: у `BpmnError`, `MermaidError`, `WireflowError` есть `problems: string[]`,
у PlantUML (`checkPlantUml`) и D2 — только `message`. Предупреждения после PR #76 идут через
общий `warnDiagram(file, message)` (`src/core/render/warnings.ts`): он печатает `⚠` в stdout и
считает их для `--strict`. Форма строки — документированный контракт (cli-commands, скилл
`c4builder`), её закрепляют тесты:

| Движок | Ошибка / предупреждение |
|---|---|
| PlantUML `.puml` | `line N: <msg>`; предупреждение #60 — `line N: <Macro> to undeclared element "<alias>"` |
| PlantUML `.iuml` | `<msg>` (без строки) |
| D2 | `D2 compile error (<abs>):\n<rel>:<line>:<col>: <msg>…`; сырой JSON движка — `[{range: "<rel>,L:C:B-L:C:B", errmsg}]` |
| BPMN | `<id> [<rule>] <msg>` (lint, layout-warning); `<id>: <msg>` (предупреждения разбора); `invalid BPMN XML: … line: L, column: C, …` (позиция XML-парсера с 0 внутри текста), `layout failed: …`, `render failed: …` |
| mermaid | `line N: <msg>` или `<msg>`; в `<msg>` движок может сам вписать `on line N, column M`, `at offset: K` |
| wireflow | `node "<id>": …`, `edge "<id>": …`, `card "<id>": …`, `group "<id>" …`, `edge #i: …`; `invalid JSON: … at position K (line L column C)` |

## Goals / Non-Goals

**Goals:**
- Структурное замечание из каждой ошибки и предупреждения, без изменения текстового вывода.
- Три машинных формата поверх одной модели. В stdout ничего, кроме отчёта.
- Аннотации на нужной строке и для BPMN и wireflow, у которых движок даёт только id.

**Non-Goals:**
- Новые проверки. Смысловые проверки — #60 и #59.
- SARIF и прочие форматы. Модель позволит добавить их одним форматтером.
- Смещение строки для файлов с несколькими `@startuml` (существующее ограничение `check`).
- Запись отчёта в файл (`--output`): достаточно перенаправления stdout.

## Decisions

### 1. Структура у источника, текст — из структуры

Рендерер, который находит нарушение, сразу знает строку, правило и id элемента, поэтому он и
отдаёт замечание структурой — `DiagramProblem` (`src/core/render/problem.ts`):
`{ message, line?, column?, rule?, element?, elementInMessage?, file?, text? }`. Печатная строка
(`⚠ <file>: …`, `✗ <file>: …`, `message` ошибки сборки) собирается из неё одной функцией
`problemText` — байт в байт как раньше:
- `rule` без `elementInMessage` → `<element|-> [<rule>] <message>` (bpmnlint, раскладка BPMN);
- иначе `line N: ` (если есть `line`), `<element>: ` (если есть `element` и он не входит в
  `message`) и `message`;
- `text` — готовая печатная строка, когда движок сам вписал позицию в формулировку (XML-парсер
  moddle, `JSON.parse`, mermaid): вывод прежний, а `message` — без позиции, позиция — в
  `line`/`column` (с 1). Позицию разбирает сам рендерер, который знает формат своего движка.

`elementInMessage` — id входит в текст по форме движка: wireflow (`edge "e1": …`, вид узла
значим для чтения, поэтому `message` — вся строка) и связь C4 (`… undeclared element "x"`).
Так префикс `<id>: ` в аннотации решается по структуре, а не поиском подстроки (короткий id `e`
нашёлся бы в любом тексте).

Источники:
- `warnDiagram(file, problem)` принимает структуру, слушатель `captureDiagramWarnings` получает
  `(file, problem)`; `check` берёт путь из слушателя, а не подменяет его файлом-entry;
- ошибки — общий базовый класс `DiagramError` с `details: DiagramProblem[]` (структура) и
  `problems: string[]` (печатные строки без пути, их печатает текст `check`). `BpmnError`,
  `MermaidError`, `WireflowError` строят `message` и `problems` из `details` через
  `problemText`; `D2Error` — тоже `DiagramError`, его `problems` — прежний многострочный
  `message` целиком. Одна проверка `isDiagramError` вместо перечня классов;
- PlantUML: `check` берёт `line` и текст из `ERROR\n<N>\n<msg>` движка и бросает `DiagramError`;
- `plantumllint` отдаёт `{ line, rule: 'undeclared-element', element, elementInMessage }`;
- `lintBpmn` и `renderWireflowSvg` отдают структуры; их юнит-тесты сравнивают печатные строки
  через `problemText` (ожидания не менялись, поменялся только помощник теста).

Прежнее решение — разбирать готовый текст регулярками по грамматике движка (`parseProblem`) —
отменено по ревью: смена формулировки в рендерере тихо портила отчёт (`rule: null`, позиция в
`message`, а значит и в fingerprint), а короткий id гасил префикс. Теперь смена формы замечания
— правка типа, её ловят компилятор и тесты. Регулярки остались только там, где движок отдаёт
позицию лишь текстом (moddle, `JSON.parse`, mermaid), и живут в рендерере этого движка.

### 2. D2 — структура из ответа движка

Текст ошибки D2 многострочный, а путь в `errmsg` отсчитан от общего корня виртуальной fs,
и из `check` его не восстановить. Ответ движка (`[{range, errmsg}]`) `renderD2` разбирает один
раз и строит из него и прежний `message` (`D2 compile error (<abs>):\n` + `errmsg` построчно),
и `details: { file: abs, line, column, message }[]` (`range` — `<key>,L:C:B-…`: позиции с 0,
ключ до последней запятой перед позицией, путь = `root + key`; `errmsg` без префикса
`file:line:col: `). Если ответ движка другой (не JSON), `details` содержит одно замечание без
позиции с исходным текстом.

### 3. Перехват предупреждений

`warnings.ts` получает `captureDiagramWarnings(listener | null)`. Пока слушатель установлен,
`warnDiagram` вызывает его с `(file, problem)` вместо печати; счётчик для `--strict` растёт как
раньше. `check` в машинном формате ставит слушатель на время своей работы. Сборка и dev-сервер
слушатель не ставят, их поведение не меняется.

### 4. Сбор в check

Цикл по файлам один на оба режима (`checkFiles`): проверка файла, счёт его предупреждений,
брошенная ошибка. Режимы различаются только обработкой результата: `text` печатает `✓`/`✗`
(строки `problems` или текст ошибки), машинный формат собирает `Diagnostic[]` и печатает их
одним блоком в конце — это нужно `json` и `gitlab` (один массив).
- брошенная ошибка: `DiagramError` → `details`; прочее (`ENOENT`, неподдерживаемое
  расширение, не-`Error` из чужого кода) → `{ message: errorText(e) }` — `String(e)`, если
  `message` нет;
- предупреждение из слушателя → `severity: "warning"`, путь — из слушателя;
- `file` замечания (импорт D2) важнее проверяемого файла; путь нормализуется до физического
  каталога (см. §5);
- одинаковые по всем полям (`file`, `line`, `column`, `engine`, `severity`, `rule`, `element`,
  `message`) замечания схлопываются по всему отчёту: ошибка в общем импортируемом `.d2`
  иначе повторялась бы за каждый импортирующий файл.

`engine` определяется таблицей `CHECKERS`: у каждого суффикса пара `{ engine, run }`.
Позиция по id (`locate(source, element, engine)`) — регулярное выражение
`\bid\s*=\s*(["'])<id>\1` для BPMN и `"id"\s*:\s*"<json-escaped id>"` для wireflow. Строка и
колонка считаются по индексу совпадения (`positionAt` из `src/util/text.ts`, общий с mermaid),
исходник читается заново только при наличии такого замечания.

Выход явный в обоих режимах и при коде 0: висящий handle упавшего движка (воркер D2, окно
jsdom) иначе подвесил бы CI. `process.exit` вызывается из колбэка последней записи в stdout и
stderr, чтобы не обрезать отчёт в pipe (на macOS запись в pipe асинхронна).

### 5. Форматтеры — чистые функции

`check.report.ts`: `formatJson`, `formatGithub`, `formatGitlab` принимают
`(diagnostics, { base })` и возвращают строку. Их покрывают юнит-тесты без запуска движков.
`base` для путей: `json` — `cwd`; `github` — `GITHUB_WORKSPACE ?? cwd`; `gitlab` —
`CI_PROJECT_DIR ?? cwd`. Внутри замечание хранит абсолютный путь, относительный считается
форматтером. База и каталоги файлов приводятся к физическому пути (`realpath`, если каталога
нет — как есть): `cwd` процесса физический (`/tmp` → `/private/tmp` на macOS), и база из
переменной CI через симлинк дала бы `../../private/tmp/…`.

- github: `::<error|warning> file=…,line=…,col=…,title=c4builder <engine>[ [<rule>]]::<text>`.
  Экранирование данных: `%`→`%25`, `\r`→`%0D`, `\n`→`%0A`; в свойствах ещё `:`→`%3A`,
  `,`→`%2C`. `<text>` — `message`, к которому спереди добавляется `<element>: `, если id не
  входит в него по форме движка (`elementInMessage`, §1) — это bpmnlint.
- gitlab: `fingerprint` — sha256 от `path\0check_name\0element\0message\0<n>`, где `n` —
  номер одинакового замечания в файле. Строки нет ни в хэше, ни в `message` (§1): сдвиг кода
  не превращает замечание в «новое» в виджете MR. `severity`: `major` / `minor`.
- json: `JSON.stringify(list, null, 2)`, ключи в порядке модели.
- Замечание без движка (неподдерживаемое расширение): `title=c4builder`, `check_name: "c4builder"`.
- База считается `reportBase(format, env, cwd)` в том же модуле — её тоже покрывает юнит-тест.

### 6. Опции CLI

`new Option('--format <format>', …).choices([...])` в `dispatch.ts`: неизвестное значение
commander отклоняет со списком допустимых и кодом 1. Для `--json` уже есть опция `doctor`, её
описание становится «for `doctor` and `check`». В `cmdCheck` формат вычисляется как
`opts.format ?? (opts.json ? 'json' : 'text')`. Строку использования `check` без файлов не
трогаем: её фиксирует сценарий #76.

`--files-from <file>` (`-` — stdin): пути по одному на строку, пустые строки пропускаются,
список добавляется к позиционным аргументам. Так список изменённых файлов из `git diff` уходит
в один вызов — и один отчёт. Прежний CI-фрагмент через `xargs` ломался: `xargs` делит длинный
список по своему буферу на несколько вызовов, и машинный формат печатал несколько JSON-массивов
подряд. Пустой список — пустой отчёт и код 0 (в `text` тоже код 0 без вывода: «изменённых
диаграмм нет» — не ошибка вызова). Нечитаемый файл списка — ошибка на английском и код 1.

Опции глобальные (commander не знает подкоманд), поэтому `--format` и `--files-from` с любой
другой командой или сборкой — ошибка на английском и код 1 (`--format is only supported by
check (use --json for doctor)`): иначе `doctor --format json` молча печатал бы текст с кодом 0.

Лог `resolveJava` передаётся в проверку параметром: в машинном формате — `console.error`, в
текстовом — `console.log`. Модульного флага нет.

CI-фрагменты сайта: `git -c core.quotePath=false diff --name-only … | c4builder check --format
… --files-from -` (кириллица в путях без экранирования), pathspec wireflow —
`'*.wireflow.json' 'wireflow.json' '*/wireflow.json'` (как на странице «Диаграммы»;
`'*wireflow.json'` ловил бы `mywireflow.json`). GitLab — изменённые в MR файлы от
`$CI_MERGE_REQUEST_DIFF_BASE_SHA`; в образе c4builder нет `git`, поэтому джоба на `node:24` с
npm-пакетом. Сайт публикуется при merge до релиза, поэтому версия закреплена на первой с
`--format` и `--files-from` — `0.15.0`, и это написано рядом с фрагментами.

## Risks / Trade-offs

- [Позиция только в тексте движка] → moddle, `JSON.parse` и mermaid отдают позицию лишь в
  формулировке, её разбирает рендерер этого движка. Если формулировка изменится, позиция
  станет `null`, а текст — прежним. Митигация: юнит-тесты на каждый такой случай и e2e
  `check --format json` с `line`/`column`.
- [Поиск id регуляркой] → id внутри комментария или строки найдётся раньше объявления, и
  строка будет неточной. Это редкость, а ошибкой стала бы только позиция аннотации.
- [Зависимость от PR #76] → при правках #76 нужен rebase; конфликт возможен в `check.ts` и
  `warnings.ts`.
- [Пустой отчёт без файлов] → отличается от `text` (usage, код 1). Сознательно: это удобнее
  для CI над diff; в спеке записано отдельным требованием.
