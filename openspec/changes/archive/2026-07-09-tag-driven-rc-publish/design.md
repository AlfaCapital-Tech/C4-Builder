## Context

Пакет `@alfacapital-tech/c4builder` публикуется в npm через `.github/workflows/publish.yml`. Текущая логика: триггер `push` в `master` + `workflow_dispatch`; шаг публикации сравнивает `npm view … version` (это `latest`) с версией из `package.json` и при различии делает `npm publish --provenance --access public` — **без `--tag`, то есть всегда в `latest`**. Аутентификация — OIDC trusted publishing (`id-token: write`), статических токенов нет.

Готовится крупный рефактор в ветке `refactor/phoenix`. Нужно публиковать релиз-кандидаты так, чтобы они не попадали к пользователям `0.2.x` через `npm install`, но были доступны тестерам осознанно.

Опубликованное состояние на момент change: `latest = 0.2.25`, `package.json = 0.2.25`.

## Goals / Non-Goals

**Goals:**
- Публикация происходит только по явному действию — push git-тега `v*`.
- Пререлизы (`0.3.0-rc.N`) публикуются под dist-tag `rc`, не смещая `latest`.
- Стабильные версии публикуются в `latest`.
- Защита от рассинхрона строки тега и версии в `package.json`.
- Повторный запуск workflow для уже опубликованной версии не падает.
- Provenance и OIDC сохраняются без новых секретов.

**Non-Goals:**
- Автоматический bump версии в CI (версию задаёт разработчик через `npm version` локально).
- Изменение тестового workflow `ci.yml` и логики рендера.
- Введение нескольких пререлизных каналов (`beta`, `next`) — сейчас только `rc`.
- Автоматический changelog / GitHub Releases.

## Decisions

### D1. Триггер: push git-тега `v*` вместо push в master

Публикация вешается на `on: push: tags: ['v*']` (+ `workflow_dispatch`). Триггер `push` в `master` **убирается**.

Почему: публикация становится явным намерением (push тега), а не побочным эффектом мержа. Тег может указывать на коммит ветки `refactor/phoenix` — RC выпускается без мержа в master. Убирая master-триггер, исключаем двойную публикацию (тег + мерж финала).

Альтернативы:
- *Триггер на ветку `refactor/phoenix`* — публиковал бы на каждый коммит (шумно), и опасный «version-diff» гейт мог бы протолкнуть пререлиз в `latest`. Отклонено.
- *Оставить master-триггер параллельно с тегами* — риск двойной публикации финала. Отклонено.

### D2. Выбор dist-tag по семантике версии

Версия читается из `package.json`. Наличие `-` = пререлиз → `npm publish --tag rc`. Иначе → публикация в `latest` (без `--tag`). Извлечение выполняется простой проверкой строки версии в shell.

Почему `rc` фиксированным словом, а не парсингом preid: у нас единственный пререлизный канал; жёсткое `rc` проще и исключает опечатки в теге. (При версии `0.3.0-rc.1` npm-семантика пререлиза сама по себе исключает её из диапазонов `^0.2.x` — это второй, независимый слой защиты помимо dist-tag.)

### D3. Гейт синхронизации тег↔версия

Перед публикацией: `test "v$(node -p 'require("./package.json").version')" = "$GITHUB_REF_NAME"`, иначе `exit 1`.

Почему: `npm publish` берёт версию из `package.json`, игнорируя строку git-тега. Без гейта тег `v0.3.0-rc.1` при забытом bump опубликовал бы `0.2.25`. Это единственный реальный footgun схемы. Эргономический контур `npm version <v>` (правит `package.json` + коммит + тег синхронно) предотвращает рассинхрон на входе, гейт — страховка на случай ручного тега.

### D4. Гейт идемпотентности (сохраняется)

Оставляем проверку из текущего workflow: `CURRENT=$(npm view … version …)` vs `LOCAL`; если версия уже в реестре — skip. Уточнение под пререлизы: сравнение должно учитывать, что публикуемая версия может быть пререлизной, поэтому проверяем присутствие конкретной версии в реестре (`npm view <pkg>@<version> version`), а не только `latest`.

### D5. Provenance / OIDC без изменений

`permissions: id-token: write`, `npm publish --provenance --access public`, `registry-url: https://registry.npmjs.org`. Модель аутентификации не меняется.

## Risks / Trade-offs

- **Рассинхрон тег↔версия** → гейт D3 + рекомендованный флоу `npm version`.
- **Пуш стабильного тега ниже текущего `latest`** (например `v0.2.24`) сместил бы `latest` назад → на практике npm не даст переопубликовать существующую версию (гейт D4 → skip); дисциплина версий. Отдельный guard не вводим (overkill).
- **Гейт идемпотентности по `latest` вместо конкретной версии** дал бы ложный «нужно публиковать» для пререлиза → D4 уточнён на проверку присутствия конкретной версии.
- **Забыли `--tag rc` для пререлиза** → пререлиз ушёл бы в `latest`; предотвращается тем, что выбор тега вычисляется автоматически из версии (D2), а не задаётся руками.

## Migration Plan

1. Переписать `.github/workflows/publish.yml`: триггер (D1), гейт синхронизации (D3), выбор dist-tag (D2), уточнённый гейт идемпотентности (D4), сохранить OIDC/provenance (D5).
2. Дополнить `README.MD` секцией про установку `@rc`.
3. Проверка вживую: с ветки `refactor/phoenix` — `npm version 0.3.0-rc.1 -m "rc: %s"` + `git push --follow-tags`; убедиться, что опубликовано под `rc`, а `latest` остался `0.2.25` (`npm view @alfacapital-tech/c4builder dist-tags`).

Откат: вернуть предыдущую версию `publish.yml` (git revert); опубликованные пререлизы при необходимости снять `npm dist-tag rm … rc` / депрекейтнуть.
