# Design

## Context

`build()` (`src/core/build.ts`) идёт строго по фазам: бэкап `dist → dist_bk` → скан → `await
generateImages` → компоновка → llms → `afterBuild`; `generateImages` (`src/core/render/diagrams.ts`)
ждёт все очереди и пишет `.c4builder.cache` один раз в `finally`. PlantUML — отдельный `spawn
java -pipe` на диаграмму, пул `renderConcurrency()` = `min(4, CPU−1)` (переопределяется
`C4BUILDER_RENDER_CONCURRENCY`), восстановление из кэша — копия из `dist_bk` в той же очереди.
Компоновка читает картинки только при `embedDiagram` (base64), иначе ей нужны лишь пути.
`dispatch.ts` при `--site -w` регистрирует watcher, ждёт полный `build()` и только потом
`cmdSite(...)` → `listen`; правка во время первой сборки ставит флаг, который никто не
обрабатывает. Livereload — SSE `/__livereload` с событиями `reload`/`agent`/`delivered`, клиент
делает `location.reload()` с восстановлением прокрутки. Сервер не знает, какая страница открыта:
`<page>.md` уходит прямо в `express.static`.

## Goals / Non-Goals

**Goals:**
- Сервер отвечает через секунды при любом размере проекта; читатель видит нужные ему диаграммы
  раньше остальных.
- Ничего не меняется для обычной сборки, golden и `check`, кроме момента записи кэша.

**Non-Goals:**
- Долгоживущий PlantUML-процесс (`-pipe` с несколькими диаграммами) — отдельный change: он
  меняет движок и требует проверки детерминизма и обработки ошибок в потоке.
- Отложенный рендер без `-w` (`--site` без watch, обычная сборка, CI): выход должен быть полным.
- Рендер по требованию (только открытые страницы): после старта всё равно дорисовываем всё,
  иначе `llms`, complete-документ и поиск остаются с заглушками.

## Decisions

**1. Один `build()` с опцией `deferImages`, а не второй конвейер.** `build(options, cache,
plugins, { deferImages: true })` → `generateImages` в этом режиме делит диаграммы на три группы:
есть в кэше и `dist_bk` (копируются сразу), `soft` и обычные без кэша. Для двух последних сразу
пишется заглушка `rendering…` (`pendingPlaceholderSvg`, растеризуется при PNG), а `build()`
возвращает `{ pending: DiagramQueue }` вместо ожидания. Компоновка, llms, `afterBuild` идут как
обычно поверх заглушек. Альтернатива — отдельная «быстрая» сборка для OpenSpec — отвергнута:
проблема не в плагине, а в любых страницах без кэша.

**2. Очередь с приоритетом.** `DiagramQueue` — массив задач в порядке дерева плюс `prioritize
(pageMd: string)`: задачи, чей выход лежит в папке страницы (`path.dirname(relOut) ===
dirname(page)`), переставляются в голову. Воркеры (`runPool` с общим индексом) заменяются на
`shift()` из очереди — та же степень параллелизма, то же поведение при ошибках. Middleware
dev-сервера перед `express.static` на `GET *.md` вызывает `prioritize`. Событие `image`
(`{ path }`) эмитится по готовности каждой задачи через существующий `reloadEmitter`.

**3. Клиент: подмена `<img>`, затем общий reload.** Клиентский сниппет livereload получает
обработчик `image`: для каждого `<img>` с совпадающим `src` (с учётом `encodeURI`) заменяет
`src` на тот же путь с `?v=<ts>` — без перезагрузки, прокрутка на месте; при `embedDiagram`
подменять нечего — ждём финального reload. Когда очередь пуста, `dispatch.ts` запускает обычную
пересборку (всё в кэше → доли секунды) и эмитит `reload` — это закрывает `embedDiagram`,
complete-документ, `llms-full` и «правки во время рендера» (флаг `attemptedWatchBuild` теперь
проверяется по окончании очереди, что заодно чинит потерю правки во время первой сборки).

**4. Ошибки в фоне — как у soft.** В отложенном режиме каждая задача ловит свою ошибку: пишет
`errorPlaceholderSvg`, печатает `✗ file: reason`, чексумма не сохраняется (следующая пересборка
перерисует). Сервер не падает. Ошибки скана/компоновки до `listen` ведут себя как раньше —
сервер не стартует.

**5. Инкрементальная запись кэша.** `generateImages` сохраняет `.c4builder.cache` после каждой
успешной задачи с дебаунсом 500 мс и в `finally`; набор чексумм — `old ∩ успешные`, как сейчас,
но накапливается постепенно. В обычной сборке на второй прогон это не влияет (golden
«повторная сборка» остаётся эталоном). При прерывании сигналом `finally` может не выполниться —
поэтому дебаунс, а не «в конце».

**6. Вывод сервера.** Порядок строк: `serving your docsify site`, `go to …`, подсказки, затем
`rendering N diagrams in background…` и по окончании `rendered N diagrams in T s` (вне TTY —
только эти две строки, без `\r`). Строка `serving` раньше рендера важна для скилла
`c4builder-review` и `test/helpers.serveSite`, которые ждут её.

**7. CI-кэш и параллелизм — документация, не код.** Тёплый старт в CI = кэш `<distFolder>/` и
`.c4builder.cache` между джобами (чексуммы без абсолютных путей; условия — те же версии jar и
пакетов, тот же шрифтовый режим). `pages.yml` сайта документации получает `actions/cache` на эти
пути как пример. `C4BUILDER_RENDER_CONCURRENCY` описывается в разделе «Кэш рендера» и в CI.

## Risks / Trade-offs

- [Заглушки попадают в выход при падении сервера до конца очереди] → заглушки живут только в
  `-w`; следующая сборка их перерисует (чексумм для них нет). В документации: `-w` — не
  источник артефактов для публикации.
- [Много `image`-событий на большом проекте] → события лёгкие (путь), клиент меняет только
  совпавшие `<img>`; финальный reload один.
- [Приоритет по папке страницы не ловит диаграммы, на которые страница ссылается из другой
  папки] → они дорисуются в общем порядке; совпадение по папке покрывает штатную раскладку.
- [Изменение `runPool` задевает обычную сборку] → очередь без `prioritize` ведёт себя как
  текущий индекс; golden и `diagram-deps` — регрессия.
- [Watcher замечает запись заглушек/картинок в dist] → dist уже исключён фильтром watcher'а.

## Migration Plan

Флагов нет: `--site -w` становится быстрее сам. Обычная сборка меняет только момент записи
кэша. Откат — убрать `deferImages` из вызова в `dispatch.ts`.
