## Context

- Клиентский код вопросов и feedback — inline-сниппет `commentsSnippet()` в
  `src/cli/commands/site.comments.ts`, который dev-сервер вставляет в HTML только при `-w`.
  В нём уже есть всё, что нужно review: кнопки у выделения, поповер, захват цитаты и раздела
  (`headingBefore`), индекс текста страницы и подсветка (`textIndex`, `wrapRange`, `locate`:
  поиск цитаты сначала в своём разделе, затем по странице).
- Карта «страница → исходники» (`PageSources`, абсолютные пути) строится в `generateWebMD` и
  возвращается из `build()`, но в `BuildCtx` плагинов не попадает; `afterBuild` получает только
  `distFolder` и опции.
- Плагины уже умеют копировать ассеты в `dist/vendor/plugins/<name>/` и подключать их в
  `index.html` при любом шаблоне; `${ENV}` в опциях подставляется при загрузке.
- Потребитель arch собирает превью каждого MR в GitLab Pages в подкаталог `mr-<IID>/`, ветку по
  умолчанию — в корень.
- Публичный репозиторий: никаких адресов конкретного GitLab ни в коде, ни в документации.

## Goals / Non-Goals

**Goals:**
- Ни одного своего сервиса: только статика и GitLab API из браузера читателя.
- Один клиентский код выделения и подсветки на три адресата: вопрос в файл, feedback агенту,
  discussion в MR.
- Комментарий не теряется ни при каких правках текста: худший случай — **outdated** в панели.

**Non-Goals:**
- Комментарии к диаграммам (SVG-текст не выделяется как текст страницы).
- Редактирование и удаление комментариев со страницы — это делается в GitLab.
- Уведомления — их шлёт GitLab.
- Обработка комментариев агентом — отдельный change в плагине marketplace; здесь только формат
  метаданных.
- Другие хостинги кода (GitHub и т.п.): адаптер хранилища появится, когда будет второй.

## Decisions

### D1. Без своего backend — GitLab API из браузера

Discussions MR дают хранение, авторство, треды, resolve, уведомления и показ в MR.
Альтернативы: свой сервис с БД — пришлось бы писать то же самое, плюс авторизацию; коммиты
комментариев в `.md` — Pages только для чтения, и параллельные ревьюеры конфликтуют; issues —
нет привязки к строкам и к MR.

### D2. Встроенный плагин, а не ядро

`src/plugins/gitlab-review/` рядом с `openspec` и `openapi`: фича опциональная и завязана на
GitLab, а API плагинов (ассеты + `afterBuild`) её покрывает. Ядро меняется в одном месте —
карта страниц в `BuildCtx` (D3).

### D3. Карта страниц в `afterBuild`

`BuildCtx.pages: PageSources` — та же карта, что возвращает `build()`; `runAfterBuild`
получает её из `build.ts`. Плагин переводит абсолютные пути в пути от корня репозитория:
`CI_PROJECT_DIR`, иначе cwd. Пути вне корня отбрасываются: файлы из архивов плагинов (`openapi`)
в репозитории MR не лежат, комментарии к ним будут без позиции.

### D4. Общий клиентский модуль

Выделение, поповер, захват цитаты, индекс текста и подсветка выносятся из `commentsSnippet` в
статический ассет `site-annotate.js` (ES5, как сейчас, без сборщика): глобальная функция
принимает список кнопок-адресатов (подпись, отправка) и цитаты для подсветки. Dev-сервер
подключает его с адресатами Question/Feedback, плагин — с адресатом Comment. Альтернатива —
копия кода в плагине; две копии поиска цитаты разойдутся при первой же правке.

В `site -w` dev-сервер ставит в `<head>` признак `window.__c4builderDevServer`; скрипт плагина
при нём не запускается (спека `site-comments`).

### D5. Вход: OAuth 2 authorization code + PKCE

Публичное приложение GitLab без секрета, `scope=api` (у `read_api` нет записи notes, более
узкого scope на запись нет). Поток:
1. панель генерирует `code_verifier` и `state`, кладёт их и адрес возврата в `sessionStorage`,
   уходит на `${gitlabUrl}/oauth/authorize`;
2. `c4b-oauth.html` (в корне каждой сборки, в том числе ветки по умолчанию) меняет `code` на
   токен через `POST ${gitlabUrl}/oauth/token`, сверяет `state`, кладёт токен в
   `sessionStorage` и делает `location.replace` на адрес возврата — только того же origin.

Один `redirectUri` на все превью: GitLab сравнивает redirect URI точно, без масок, а превью
`mr-<IID>/` и корень Pages на одном origin, поэтому `sessionStorage` общий. Refresh token не
храним: токен GitLab живёт 2 часа, затем повторный вход (черновик сохраняется).

### D6. Чтение

При загрузке: `GET …/merge_requests/:iid/versions` (последняя версия — для плашки устаревшей
сборки, версия с `head_commit_sha = sha` — для позиций) и
`GET …/merge_requests/:iid/discussions?per_page=100` по `x-next-page`. Берутся discussions,
у первой note которых есть блок `c4builder-review`. Список кэшируется на загрузку страницы;
переходы docsify по hash его не перезапрашивают; кнопка **Refresh** перезапрашивает.

### D7. Создание и позиция

Тело:

```
<комментарий>

> <цитата>

§ <раздел> · [<страница>](<url превью>#/<страница>)

<!-- c4builder-review {"v":1,"page":…,"file":…,"quote":…,"prefix":…,"suffix":…,"section":[…],"sha":…} -->
```

Позиция:
1. файл — первый из исходников страницы, где нашлась цитата: сырой файл
   `GET …/repository/files/:path/raw?ref=<sha>`, построчно без inline-разметки (`**`, `_`,
   обратные кавычки, `[текст](url)` → текст, HTML-теги, `|` таблиц); строка — начало совпадения;
2. diff — из версии MR сборки; строка позиционируется, только если она добавлена в MR
   (`+` в hunk). Тогда `position_type: text`, `base_sha`/`start_sha`/`head_sha` версии,
   `new_path`, `new_line`;
3. иначе, а также при 400 от GitLab на позицию — discussion без позиции.

Неизменённые строки внутри hunk требуют `old_line` и `new_line` — пока не позиционируются:
файлы change'ей в MR новые целиком, для них позиция есть всегда. Добавить, если начнут ревьюить
правки существующих specs.

### D8. Повторная привязка

Поиск по нормализованному тексту (`collapse`), порядок — по спеке. Текущий `locate` уже даёт
«точно в разделе → точно на странице»; добавляются:
- контекст `prefix`/`suffix` — выбирает среди нескольких точных совпадений в разделе;
- единственность для **moved**: несколько совпадений вне раздела без контекста — не гадаем;
- нечёткий поиск — приближённое вхождение подстроки (алгоритм Селлерса, DP по редакционному
  расстоянию с нулевой первой строкой): O(длина текста × длина цитаты), цитата ≤ 200 символов,
  поэтому хватает даже всей страницы. Порог — расстояние ≤ 25% длины цитаты. Ищем в своём
  разделе; раздел переименован — по странице.

Своя реализация на ~30 строк вместо `diff-match-patch`: новая клиентская зависимость ради одной
функции не нужна. Позицию в MR трассирует сам GitLab; на сайте она не используется.

**outdated** ссылается на `${projectUrl}/-/compare/<sha комментария>...<sha сборки>`,
`projectUrl` — `web_url` из `GET /projects/:id`, один запрос при входе.

### D9. Строки UI

Через `site.i18n.ts` (en/ru, выбор языка как у вопросов). Значения в `review.json` и тексты
тела комментария, которые генерирует код, — английские (`§`, ссылка); комментарий читателя —
как написан.

## Risks / Trade-offs

- [Токен `api` в браузере при `executeScript: true`] JS из markdown ветки MR исполняется на
  той же странице и может украсть токен ревьюера — с доступом ко всему, что тот видит в GitLab.
  → Токен только в `sessionStorage`, срок 2 часа, без refresh; документация рекомендует
  выключать `executeScript` для сборок превью; узкого scope GitLab не даёт.
- [Общий origin Pages] Без unique domain другие проекты группы на том же origin в той же вкладке
  читают `sessionStorage`. → Документация требует unique domain для Pages проекта.
- [CORS у `/oauth/token` и `/api/v4`] Без CORS у обмена кода на токен поток из браузера
  невозможен. → Первая задача — спайк на целевом GitLab; если CORS нет, change
  останавливается до решения (прокси обмена кода — вне scope).
- [Цитата из рендера не совпала с markdown] Таблицы, сложная разметка → нет строки → discussion
  без позиции. На сайте привязка работает, в MR виден как общий тред с цитатой — допустимо.
- [Превью отстаёт от MR] Комментарий к версии сборки может сразу оказаться **changed** после
  публикации нового превью. → Плашка устаревшей сборки (спека) и привязка к `sha` сборки.

## Migration Plan

Opt-in: без строки плагина в `.c4builder` ничего не меняется. Для потребителя:
1. OAuth-приложение GitLab: не confidential, scope `api`, redirect URI `<pages-url>/c4b-oauth.html`;
2. `["gitlab-review", { "gitlabUrl": "…", "clientId": "…" }]` в `.c4builder`;
3. сборка ветки по умолчанию (публикует callback в корень), затем превью MR.

Откат — убрать строку плагина; discussions в MR остаются обычными тредами.

## Open Questions
