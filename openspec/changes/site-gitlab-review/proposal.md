## Why

Вопросы со страницы (site-comments) и feedback агенту (site-agent-feedback) работают только в
локальном `site -w` одного человека. Обсудить change или архитектуру с коллегами асинхронно
нельзя: превью MR на статическом хостинге (GitLab Pages) только для чтения, а комментарии к сырому
markdown в MR неудобны тем, кто читает сайт с диаграммами, — бизнесу, аналитикам, лидам.
Нужен совместный review прямо на собранном сайте, без своего сервера: хранилище, авторы,
уведомления и resolve уже есть у GitLab в discussions merge request.

## What Changes

- **Встроенный плагин `gitlab-review`**: подключает к статическому сайту панель review. Читатель
  входит через GitLab (OAuth 2 authorization code + PKCE, публичное приложение, без секрета) и
  видит discussions MR, из которого собран сайт, с подсветкой цитат на страницах.
- **Комментарий со страницы**: тот же жест, что у Question (выделил → написал), но комментарий
  создаётся discussion в MR от имени читателя. Если строка цитаты есть в diff MR, discussion
  привязывается к ней (виден на вкладке Changes); иначе — общий discussion MR. В теле —
  комментарий, цитата, ссылка на страницу превью и скрытый блок метаданных для повторной
  привязки и для агента.
- **Ответ и resolve** со страницы; фильтр открытые/решённые; плашка, если сайт собран со старого
  коммита MR.
- **Повторная привязка после правок**: комментарий ищется на странице по цитате и её контексту в
  своём разделе, затем по всей странице, затем нечётко; статус привязки — точно / сдвинут /
  изменён / устарел. Непривязанные комментарии не теряются, а показываются в панели с исходной
  цитатой. Автоматически ничего не резолвится.
- **Конфиг**: `["gitlab-review", { "gitlabUrl": …, "clientId": … }]`; проект, MR, коммит и адрес
  callback по умолчанию берутся из переменных GitLab CI. Без MR (сборка ветки по умолчанию,
  локальная сборка) панель не показывается, сайт собирается как раньше.
- **Хук `afterBuild` получает карту страниц**: страница сайта → исходные файлы (то, что сейчас
  знает только dev-сервер `site -w`), чтобы плагины могли сопоставить страницу с файлом в
  репозитории.
- **Общий клиентский код выделения и подсветки**: UI выделения, поповер и поиск цитаты на
  странице выносятся из inline-сниппета dev-сервера в ассет, который используют и `site -w`, и
  плагин; меняется только адресат отправки.

## Capabilities

### New Capabilities
- `gitlab-review-plugin`: review статического сайта в discussions GitLab MR — конфиг и умолчания из
  CI, вход OAuth PKCE, чтение/создание/ответ/resolve discussions, привязка к строке diff, формат
  тела и метаданных, повторная привязка и статусы, поведение без MR и при устаревшей сборке.

### Modified Capabilities
- `plugin-system`: `afterBuild` получает карту «страница → исходные файлы».
- `site-comments`: элементы выделения могут присутствовать в статическом сайте, если подключён
  `gitlab-review` (сейчас — строго только dev-сервер); в `site -w` поведение не меняется.

## Impact

- Код: новый `src/plugins/gitlab-review/` (схема опций, `afterBuild`: `review.json` и
  `c4b-oauth.html`, клиентский ассет), `src/core/plugins/types.ts` и `hooks.ts` (карта страниц в
  `BuildCtx`), `src/core/build.ts`, вынос клиентского кода из `src/cli/commands/site.comments.ts`
  в общий ассет, `src/cli/commands/site.i18n.ts` (строки панели).
- Внешние системы: GitLab REST API v4 (merge requests, discussions, versions, diffs, repository
  files) и OAuth — из браузера читателя, CORS на стороне GitLab. Своего сервера нет.
- Потребитель: репозиторий arch — уже публикует превью MR в Pages (`mr-<IID>/`); нужно OAuth-
  приложение в GitLab и строка плагина в `.c4builder`.
- Зависимости: новых нет.
- Безопасность: токен со scope `api` живёт в браузере; при `executeScript: true` JS из markdown
  ветки исполняется рядом с ним (см. design, риски).
- Вне change: агентская сторона (`/c4builder-review` в marketplace читает discussions через
  GitLab MCP) — отдельный change в плагине marketplace.
