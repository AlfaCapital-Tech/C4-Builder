## Context

Мотивация — в `proposal.md`, требования — в `specs/openspec-plugin`. Что важно для подхода:

- Подпись пункта sidebar — имя сегмента пути страницы (`TreeItem.name`): отдельного заголовка
  у виртуальной страницы (`PageSpec`) нет. Значит, «короткая подпись» вложенного change'а — это
  последний сегмент его пути, без правки ядра.
- `addPage` создаёт недостающие промежуточные сегменты пустыми узлами и вставляет страницу в
  конец поддерева родителя: порядок в sidebar — порядок вызовов.
- Ссылка на родителя — не часть формата OpenSpec, а соглашение конкретного store; ключ должен
  задаваться в конфиге, а не зашиваться в плагин.

## Goals / Non-Goals

**Goals:** дерево «корень → подзадачи» в sidebar, таблице Changes и архиве; связи на
страницах; без опции — байт-в-байт прежний вывод.

**Non-Goals:** заголовок страницы, отличный от сегмента пути (например title из proposal) —
потребует поля заголовка в `PageSpec` и правки sidebar, отдельное изменение; вложенность
глубже одного уровня; сопоставление родителя по префиксу id без метаданных.

## Decisions

### D1. Родитель — по ключу `.openspec.yaml`, ключ — опция `parentKey`

`readMeta` читает все скаляры верхнего уровня в `Change.meta`, `schema`/`created` — как
раньше. Родитель — change того же списка, чей id равен `meta[parentKey]`. Альтернатива —
родитель по префиксу id — отвергнута: склеит несвязанные change'ы с общим началом
(`add-auth` / `add-auth-tests`).

### D2. Раскладка — отдельный модуль `layout.ts`

`layoutChanges(changes, base, { parentKey, archived })` → `Map<Change, Placement>` с путём
страницы, подписью, родителем и вложенными; `pageOrder` — родитель, сразу за ним вложенные.
Без `parentKey` все change'ы на верхнем уровне с подписью-id — рендер получает ту же раскладку
и выводит то же, что раньше. Рендер-функции принимают раскладку необязательным последним
параметром — их прежние вызовы не меняются.

### D3. Подпись — хвост id, при конфликте — полный id

Хвост после `<id родителя>-` короткий и уникален в пределах родителя, если не совпадает с
подстраницей родителя: артефакт (`design`, `tasks`, …) или `specs` дали бы коллизию путей в
`addPage`, совпадение с соседом — тоже. В этих случаях и при id без общего префикса — полный id.

### D4. Порядок — родитель раньше вложенных

Страницы добавляются в порядке `pageOrder`: под родителем в sidebar сначала его артефакты,
затем вложенные change'ы. В таблице Changes порядок внутри групп — по дате, как и раньше.

### D5. Архив — сопоставление без даты

Архивный change — `<YYYY-MM-DD>-<id>`, а ссылка пишется по активному id (подзадачи обычно
архивируются раньше корня). При `archived: true` id для сопоставления и для подписи берётся без
префикса даты. Вложенный активный change с архивным родителем остаётся на верхнем уровне
Changes — родителя в этом списке нет.

## Risks / Trade-offs

- Подписи коротких хвостов могут совпасть у разных родителей — это нормально: путь страницы
  включает родителя, коллизий путей нет.
- Смена `parentKey` меняет адреса страниц вложенных change'ов (`Changes/<родитель>/<подпись>`) —
  внешние ссылки на прежние адреса ломаются; это цена включения опции, без неё адреса прежние.
