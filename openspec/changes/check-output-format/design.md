# Design

## Context

`check.ts` проверяет файлы по очереди. Ошибку каждого движка он превращает в строки
`✗ <file>: <problem>`: у `BpmnError`, `MermaidError`, `WireflowError` есть `problems: string[]`,
у PlantUML (`checkPlantUml`) и D2 — только `message`. Предупреждения после PR #76 идут через
общий `warnDiagram(file, message)` (`src/core/render/warnings.ts`): он печатает `⚠` в stdout и
считает их для `--strict`. Форма строки — документированный контракт (cli-commands, скилл
`c4builder`), её закрепляют тесты:

| Движок | Ошибка / предупреждение |
|---|---|
| PlantUML `.puml` | `line N: <msg>`; предупреждение #60 — `line N: <Macro> to undeclared element "<alias>"` |
| PlantUML `.iuml` | `<msg>` (без строки) |
| D2 | `D2 compile error (<abs>):\n<rel>:<line>:<col>: <msg>…`; сырой JSON движка — `[{range: "<rel>,L:C:B-L:C:B", errmsg}]` |
| BPMN | `<id> [<rule>] <msg>` (lint, layout-warning); `<id>: <msg>` (предупреждения разбора); `invalid BPMN XML: …`, `layout failed: …`, `render failed: …` |
| mermaid | `line N: <msg>` или `<msg>` |
| wireflow | `node "<id>": …`, `edge "<id>": …`, `card "<id>": …`, `group "<id>" …`, `edge #i: …` |

## Goals / Non-Goals

**Goals:**
- Структурное замечание из каждой ошибки и предупреждения, без изменения текстового вывода.
- Три машинных формата поверх одной модели. В stdout ничего, кроме отчёта.
- Аннотации на нужной строке и для BPMN и wireflow, у которых движок даёт только id.

**Non-Goals:**
- Новые проверки. Смысловые проверки — #60 и #59.
- SARIF и прочие форматы. Модель позволит добавить их одним форматтером.
- Смещение строки для файлов с несколькими `@startuml` (существующее ограничение `check`).
- Вывод в файл (`--output`): достаточно перенаправления stdout.

## Decisions

### 1. Структура из текста движка, а не переделка всех throw-сайтов

`parseProblem(engine, text) → { line?, column?, rule?, element?, message }` разбирает
строку по грамматике движка из таблицы выше. Грамматика — тот же стабильный контракт,
который уже разбирают агенты. Модуль с грамматиками один, поэтому изменение формата строки
ломает один файл и его тесты. Правила:
- общее: `^line (\d+): (.*)$` → `line` и `message`;
- PlantUML: если `message` совпадает с `^\w+ to undeclared element "(.*)"$`, то
  `rule: "undeclared-element"` и `element`. Шаблон строки экспортирует `plantumllint.ts`,
  оба места используют один источник;
- BPMN: `^(\S+) \[([^\]]+)\] (.*)$` → `element` (`-` → `null`), `rule`, `message`;
  `^([^\s:]+): (.*)$` → `element` (только для BPMN: у других движков так начинаются
  `ENOENT: …`);
- wireflow: `^(?:node|edge|card|group|note) ("(?:[^"\\]|\\.)*")` → `element` через
  `JSON.parse` (так строку собирает `q()`). `message` — вся строка, потому что вид узла
  (`card`/`edge`) в ней значим.

Альтернатива — передавать `Problem` из всех мест, где бросаются ошибки, и строить текст из
него. Это около 30 мест в трёх движках, а также смена `problems`/`lintBpmn` с правкой их
юнит-тестов. Риск сдвинуть текстовый контракт выше, а пользы для этого change нет. Отказ.

### 2. D2 — структура из источника

Текст ошибки D2 многострочный, а путь в `errmsg` отсчитан от общего корня виртуальной fs,
и из `check` его не восстановить. Поэтому `renderD2` бросает `D2Error extends Error` с тем же
`message` (сборка и текст `check` не меняются) и полем
`problems: { file: abs, line, column, message }[]`. Поле собирается из `range`
(`<key>,L:C:B-…`: позиции с 0, ключ до последней запятой перед позицией, путь = `root + key`)
и `errmsg` без префикса `file:line:col: `. Если ответ движка другой (не JSON), `problems`
содержит одно замечание без позиции с исходным текстом.

### 3. Перехват предупреждений

`warnings.ts` получает `captureDiagramWarnings(listener | null)`. Пока слушатель установлен,
`warnDiagram` вызывает его с `(file, message)` вместо печати; счётчик для `--strict` растёт
как раньше. `check` в машинном формате ставит слушатель на время своей работы. Сборка и
dev-сервер слушатель не ставят, их поведение не меняется.

### 4. Сбор в check

`check` для каждого файла собирает `Diagnostic[]` и печатает их одним блоком в конце. Это
нужно `json` и `gitlab` (один массив), а для `github` порядок строк от этого не зависит.
Источники замечаний:
- брошенная ошибка: `DiagramProblems`-ошибки (`BpmnError`, `MermaidError`, `WireflowError`)
  → `problems.map(parseProblem)`; `D2Error` → `problems`; ошибка PlantUML → `parseProblem`
  по `message`; прочее (`ENOENT`, неподдерживаемое расширение) → `{ message }`;
- предупреждение из слушателя → `parseProblem(engine файла, message)`, `severity: "warning"`.

`engine` определяется таблицей `CHECKERS`: у каждого суффикса теперь пара `{ engine, run }`.
Позиция по id (`locate(source, element, engine)`) — регулярное выражение
`\bid\s*=\s*(["'])<id>\1` для BPMN и `"id"\s*:\s*"<json-escaped id>"` для wireflow. Строка и
колонка считаются по индексу совпадения, исходник читается заново только при наличии такого
замечания.

Текстовый формат остаётся старой веткой печати, без похода через модель: так байтовая
совместимость гарантирована.

### 5. Форматтеры — чистые функции

`check.report.ts`: `formatJson`, `formatGithub`, `formatGitlab` принимают
`(diagnostics, { base })` и возвращают строку. Их покрывают юнит-тесты без запуска движков.
`base` для путей: `json` — `cwd`; `github` — `GITHUB_WORKSPACE ?? cwd`; `gitlab` —
`CI_PROJECT_DIR ?? cwd`. Внутри замечание хранит абсолютный путь, относительный считается
форматтером.

- github: `::<error|warning> file=…,line=…,col=…,title=c4builder <engine>[ [<rule>]]::<text>`.
  Экранирование данных: `%`→`%25`, `\r`→`%0D`, `\n`→`%0A`; в свойствах ещё `:`→`%3A`,
  `,`→`%2C`. `<text>` — `message`, к которому спереди добавляется `<element>: `, если id в
  `message` не встречается (bpmnlint).
- gitlab: `fingerprint` — sha256 от `path\0check_name\0element\0message\0<n>`, где `n` —
  номер одинакового замечания в файле. Строка в хэш не входит: тогда сдвиг кода не
  превращает замечание в «новое» в виджете MR. `severity`: `major` / `minor`.
- json: `JSON.stringify(list, null, 2)`, ключи в порядке модели.

### 6. Опции CLI

`new Option('--format <format>', …).choices([...])` в `dispatch.ts`: неизвестное значение
commander отклоняет со списком допустимых и кодом 1. Для `--json` уже есть опция `doctor`, её
описание становится «for `doctor` and `check`». В `cmdCheck` формат вычисляется как
`opts.format ?? (opts.json ? 'json' : 'text')`. Строку использования `check` без файлов не
трогаем: её фиксирует сценарий #76.

Лог `resolveJava` в машинном формате печатается через `console.error`.

## Risks / Trade-offs

- [Разбор текста движка] → если поменять форму строки в рендерере, структура в машинном
  формате деградирует (например, `rule: null`) без падения. Митигация: e2e-тесты
  `check --format json` на каждый движок проверяют поля.
- [Поиск id регуляркой] → id внутри комментария или строки найдётся раньше объявления, и
  строка будет неточной. Это редкость, а ошибкой стала бы только позиция аннотации.
- [Зависимость от PR #76] → при правках #76 нужен rebase; конфликт возможен в `check.ts` и
  `warnings.ts`.
- [Пустой отчёт без файлов] → отличается от `text` (usage, код 1). Сознательно: это удобнее
  для CI над diff; в спеке записано отдельным требованием.
