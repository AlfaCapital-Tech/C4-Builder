## Context

После `ts-port-full` весь `src/` — строгий TypeScript, но `core/build.ts`
остаётся монолитом ~880 строк: скан (`generateTree`, `foldIncludes`), рендер
(`renderDiagram`, `generateImages`), компоуз (`compileDocument`, `generateMD`,
`generateCompleteMD`, `generateWebMD`) и оркестрация (`build`) — в одном файле
с общими замыканиями и локальными интерфейсами. Часть render- и compose-кода
уже выделена раньше (`render/{jre,d2renderer,pngraster}.ts`,
`compose/docsify.template.ts`) — монолит доразбирается в те же домены.
Golden-матрица фиксирует полный вывод трёх вариантов конфигурации.

## Goals / Non-Goals

**Goals:**
- Фазы scan / render / compose — отдельные модули со своими экспортируемыми
  типами границ; `build.ts` — только оркестрация (цель — порядка сотни строк).
- Перенос без изменения логики: golden зелёный после каждого шага выделения.
- Типы границ (дерево скана, элемент с диаграммами, колбэки прогресса) —
  публичные контракты фаз, на которые смогут опираться юнит-тесты и TeaVM-бэкенд.

**Non-Goals:**
- Изменение алгоритмов фаз, порядка обхода, формата вывода.
- Новые фичи рендера, `zod`, апгрейды зависимостей, починка легаси.
- Переработка уже выделенных модулей (`jre`, `d2renderer`, `pngraster`,
  `docsify.template`).

## Decisions

**Дробление по фактическим швам монолита, не по идеальной архитектуре.**
Модули повторяют существующие фазы: `scan/tree.ts` (генерация дерева +
`foldIncludes` + `getFolderName`), `render/diagrams.ts` (`renderDiagram`,
`generateImages`, `diagramOutputFormat`, `getMime`, `httpGet`),
`compose/markdown.ts` (`compileDocument`, `hasOwnH1`, `injectAfterFirstH1`,
три `generate*MD`). Никаких переименований функций и перестройки сигнатур
сверх необходимого для экспорта — дифф должен читаться как перенос.
- *Альтернатива (отвергнута):* заодно спроектировать «правильные» интерфейсы
  фаз (пайплайн, DI) — смешивает перенос с редизайном, ломает читаемость
  диффа; редизайн возможен позже поверх выделенных модулей.

**Типы границ живут в модуле-владельце.** Тип дерева скана — в `scan/tree.ts`,
тип задачи рендера — в `render/diagrams.ts`; compose импортирует тип дерева из
scan. Отдельного `core/types.ts` не заводим, пока нет типа с двумя владельцами.

**Порядок выделения — по потоку данных, шаг = коммит.** scan → render →
compose; после каждого шага монолит компилируется и golden зелёный. Оркестратор
ужимается естественно по мере выноса.

**Общие константы уходят к потребителям.** `FONTS_DIR`, `DEFAULT_FONT_NAME`,
`DIST_BACKUP_FOLDER_SUFFIX` и подобные переезжают в модуль единственного
потребителя; константа с двумя потребителями остаётся в `build.ts` до
появления явного владельца.

## Risks / Trade-offs

- **[Скрытая связность через замыкания монолита]** → выделение по одному шагу
  с компиляцией и golden после каждого; обнаруженная связность фиксируется
  явным параметром функции, не общим состоянием.
- **[Дифф «перенос» разъедется с «правкой»]** → правило rename-only: логика
  не меняется, форматирование не трогается; ревью сверяет тела функций.
- **[`httpGet`/серверный рендер — мёртвый или полумёртвый код уедет как есть]**
  → так и задумано: инвентаризация мёртвого кода — не этот change; переносим
  без ревизии.

## Migration Plan

1. `scan/tree.ts`: `generateTree` + `foldIncludes` + `getFolderName` + тип
   дерева; `build.ts` импортирует; golden; коммит.
2. `render/diagrams.ts`: `renderDiagram`, `generateImages`,
   `diagramOutputFormat`, `getMime`, `httpGet`; golden; коммит.
3. `compose/markdown.ts`: `compileDocument`, `hasOwnH1`,
   `injectAfterFirstH1`, `generateMD`, `generateCompleteMD`, `generateWebMD`;
   golden; коммит.
4. Ревизия остатка `build.ts` (оркестрация: бэкап dist, вызовы фаз, прогресс);
   константы — к владельцам; golden + `npm pack` санити; коммит.

Откат — по коммитам шагов; change выполняется строго после архивации
`ts-port-full`.
