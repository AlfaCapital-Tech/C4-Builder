# Design

## Context

Мотивация — в `proposal.md`. Что есть сейчас:

- `src/cli/commands/check.ts` выбирает проверку по суффиксу имени (`CHECKERS`): у файла один
  движок и одна функция `run(abs, log)`. Проверка бросает ошибку; у `DiagramError` есть
  `details` (структура для `--format`) и `problems` (печатные строки, по одной на `✗`).
  `.md` в таблице нет — отсюда `unsupported extension`.
- `src/core/scan/fences.ts` — `createFenceExtractor(langs).extract(md, base, source)`: общий для
  сборки страниц (`scan/tree.ts`, языки `plantuml`, `mermaid`) и плагина OpenSpec
  (`plantuml`, `puml`, `d2`, `mermaid`) разбор fenced-блоков. Отдаёт `content` (с обёрткой
  `@startuml`/`@enduml`, если её нет; отступ блока в списке снят) и `lineOffset`: строка N в
  `content` — строка `N + lineOffset` файла `.md`.
- `renderDiagram` при ошибке входа бросает `PlantUmlInputError` с `details[0].line` — строкой
  внутри переданного текста. Сборка печатает для блока Markdown эту строку как есть, с именем
  картинки рядом; `warnUndeclaredRels` уже принимает `lineOffset` и даёт строку страницы.
- `check` работает без проекта и `.c4builder`: не знает, страница это или артефакт плагина.

## Goals / Non-Goals

**Goals:**

- `check file.md` находит то же, что нашла бы сборка в блоках `plantuml` этого файла, и
  указывает строку файла `.md`.
- Один разбор блоков на сборку и `check` — без второй регулярки fenced-блоков.
- Вывод и коды для остальных расширений — байт в байт прежние.

**Non-Goals:**

- Блоки `mermaid`, `d2`, `puml`. `puml` и `d2` в страницах проекта остаются кодом («показать
  исходник») и рендерятся только плагином OpenSpec; без проекта `check` контекста не знает, и
  проверка дала бы ложные ошибки на примерах кода. `mermaid` сборка рендерит везде, но у файла
  в `check` один движок на все замечания — блоки двух движков в одном файле требуют движка на
  замечание. Это отдельный change, если понадобится; issue #91 просит только `plantuml`.
- Обход каталогов и glob: список файлов по-прежнему даёт вызывающий (`git diff`, `--files-from`).
- Проверка диаграмм, на которые `.md` ссылается картинкой (`![](a.puml)`), — их проверяют как файлы.
- Строка страницы в сообщениях об ошибке блока в сборке (там строка внутри блока) — не трогаем.

## Decisions

### 1. Блоки достаёт `createFenceExtractor(['plantuml'])`

Новый экстрактор на каждый файл, `extract(text, 'block')`; markdown-результат
(текст со ссылками на картинки) и имена файлов отбрасываются, нужны `content` и `lineOffset`.
Обёртка `@startuml`, снятие отступа, правила CommonMark для fence — те же, что в сборке, и
меняются вместе с ней.

Альтернатива — своя регулярка в `check.ts`: разошлась бы со сборкой на первом же краевом случае
(блок в списке, `~~~`, fence длиннее трёх символов).

Следствие: экстрактор схлопывает блоки с одинаковым содержимым в одну диаграмму. Одинаковые
блоки проверяются один раз, замечание — со строкой первого. Чтобы сообщать о каждом вхождении,
пришлось бы менять контракт экстрактора, на котором стоит сборка; ради редкого случая (два
одинаковых битых блока в одном файле) не стоит.

### 2. Общий рендер исходника PlantUML

Из `checkPlantUml` выделяется функция «отрендерить текст»: `(content, includePath, log)` →
`renderDiagram` с теми же опциями, что сейчас (SVG, `UTF-8`, вендорный шрифт, ditaa → PNG).
`.puml`/`.iuml` вызывают её как раньше; `.md` — для каждого блока с `includePath` = папка
файла `.md` (как у `.puml` и как у плагина OpenSpec: `!include` ищется рядом с исходником).
Повтор с контекстом C4 остаётся только у `.iuml`.

### 3. Строка файла `.md` в замечании

Для `PlantUmlInputError` блока: `line = e.line + plantUmlLineBase(content) + lineOffset`.
`lineOffset` переводит строку `content` в строку файла, а `plantUmlLineBase` — позицию движка
в строку `content`. Одного `lineOffset` мало (найдено на ревью, проверено на вендорном jar в
`-pipe`):

- движок считает позицию от строки `@start…`, а не от начала текста — пустая строка или
  комментарий перед `@startuml` в блоке сдвигали номер;
- директивой движок признаёт `@start` только в самом начале строки; текст без такой строки он
  оборачивает в `@startuml` сам (обёртка — позиция 0, ведущие пустые строки отброшены). Так
  считается блок, где `@startuml` стоит с отступом.

`plantUmlLineBase` — чистая функция в `src/core/render/diagrams.ts`, рядом с разбором блока
`ERROR`; позиция движка — поле `line` у `PlantUmlInputError`. Применяется только в проверке
`.md`: у `.puml` с преамбулой перед `@startuml` тот же сдвиг есть сегодня, но вывод прежних
расширений и строка блока в сборке этим change не меняются (см. Non-Goals).

Для предупреждений: `warnUndeclaredRels(relative(abs), content, svg, lineOffset)` — как в
сборке. ditaa-блок, как и `.puml` с ditaa, смысловой проверкой не проверяется.

### 4. Замечания всех блоков — одна `DiagramError` на файл

Блоки проверяются последовательно; замечания копятся и после последнего блока бросается одна
`DiagramError`: `details` — замечания блоков по порядку, `problems` — их печатные строки
(`problemText`), `message` — выводы движка через пустую строку (для `--verbose`). Существующий
цикл `checkFiles` и оба режима вывода (`✗` на каждую строку `problems`, `errorDiagnostics` по
`details`) менять не нужно.

Java резолвится один раз до цикла, если блоки есть: нет java — причина общая, одна ошибка
файла, как у `.puml`. Сбой рендера конкретного блока, не являющийся ошибкой входа (таймаут,
падение JVM без блока `ERROR`), — замечание этого блока, а не конец проверки: строка —
начало блока (`lineOffset + 1`), печатный текст — `line N:` и короткая строка
`describeRenderError` (как у `.puml`: первая строка и подсказка про `--verbose`), `message`
замечания — вывод процесса целиком, как у `.puml` в машинном формате. Проверка остальных
блоков продолжается.

Первая версия бросала такой сбой сразу («у остальных блоков та же причина»); ревью показало,
что это верно только для отсутствия java, а таймаут одного блока прятал уже найденные ошибки
соседних.

Альтернатива — остановиться на первом ошибочном блоке: противоречит критерию issue «проверяются
все блоки» и заставляет чинить по одному за запуск.

### 5. Запись в `CHECKERS`: `.md` → движок `plantuml`

`.md` добавляется последним ключом: порядок ключей — порядок в списках расширений
(`EXTENSIONS`, `EXPECTED`, строка использования, справка), прежние расширения остаются на
местах. Движок `plantuml` попадает в `engine` замечаний, в том числе при ошибке чтения файла —
как у `.puml`. Файл без блоков `plantuml` java не резолвит (JRE уже ленивый).

Суффикс — только `.md` (без `.markdown`): сборка считает страницами только `.md`.

### 6. Справка

`src/cli/help.ts`: список расширений подтянется из `EXTENSIONS`; в `about` — фраза, что в `.md`
проверяются только блоки ` ```plantuml `, в таблицу вывода — что строка ошибки блока считается
от начала файла `.md`.

### 7. Порядок замечаний `.md` в машинном отчёте — по строке

Предупреждения блоков приходят по ходу проверки, ошибки — одной `DiagramError` в конце файла,
поэтому в отчёте предупреждение второго блока стояло перед ошибкой первого. У записи `.md` в
`CHECKERS` флаг `byLine`: замечания файла стабильно сортируются по строке перед добавлением в
отчёт. Только `.md` — порядок других движков не трогаем. Текстовый режим прежний: по контракту
`cli-commands` предупреждения печатаются перед строкой результата файла.

### 8. Обёртка `@startuml` — по директиве в начале строки

`fences.ts` решал «обёртка не нужна» поиском `@start\w+` где угодно в теле блока: упоминание
`@startuml` в подписи отключало обёртку. Теперь директива ищется в начале строки
(`/^\s*@start\w+/m`). Код общий со сборкой, но картинка не меняется: текст без директивы движок
оборачивает сам; у таких блоков меняется только хэш в имени файла. Отступ перед директивой
по-прежнему допускается — имена уже отрендеренных блоков с отступом не сдвигаются.

## Risks / Trade-offs

- [`check **/*.md` на большом репозитории — java на каждый блок, ~1 с] → файлы без блоков java
  не запускают; список изменённых файлов даёт CI. Пул рендера — существующая заметка `ponytail`
  в `checkFiles`, вне этого change.
- [Ошибка внутри `!include`-файла или во втором `@startuml` одного блока: PlantUML считает
  строку от начала той диаграммы, где ошибка, и не сообщает, какая это диаграмма, — строка
  считается от первого `@start…` и укажет не ту строку `.md`] → то же ограничение есть у `.puml`
  (в справке: «the line within the diagram»); разбирать блок на диаграммы не стали. Полный
  вывод движка — в `--verbose`.
- [Сбой процесса на блоке проверен подставной `java` (скрипт через `JAVA_HOME`), а не настоящим
  таймаутом или падением JVM] → путь кода один: любой не-`PlantUmlInputError` из `renderDiagram`;
  сам разбор вывода процесса покрыт тестами `plantUmlFailure`.
- [В сборке битый блок страницы — предупреждение с заглушкой, а в `check` — ошибка и код 1] →
  так и задумано: `check` отвечает «отрисуется ли диаграмма», а не «упадёт ли сборка»; критерий
  issue требует ненулевой код.
- [Блок `plantuml`, показанный как пример заведомо битого кода, даёт ошибку] → сборка его тоже
  рендерит (заглушкой); для примера кода есть язык `puml` или `text`.
- [Одинаковые битые блоки — одно замечание] → см. решение 1.
- [`!include` блока сперва ищется в текущем каталоге, и только потом в папке файла `.md`: так
  PlantUML ведёт себя в режиме `-pipe`, одноимённый файл в cwd перекроет соседний с `.md`] →
  то же у `.puml` в `check` сегодня (обнаружено при реализации, в тесте имя библиотеки
  уникально); правка порядка поиска — вне этого change.
