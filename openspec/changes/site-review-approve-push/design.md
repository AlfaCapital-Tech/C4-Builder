## Context

Журнал ревью (`src/core/reviewlog.ts`) пишет строку в таблицу раздела `comments.heading` ближайшего
`comments.file`; маршруты `/__c4builder/review-log` (`src/cli/commands/site.ts`) — POST (запись), GET
(страница журнала или замечания страницы для подсветки), DELETE (удаление строки по ячейкам). На
странице самого журнала клиентский скрипт (`site.comments.ts`, `decorateLog`) уже находит раздел по
заголовку и вешает кнопки на строки таблицы. Движок строк — `src/core/sections.ts` (`tableRows`,
`writeRow`, `deleteRow`). Git сейчас вызывается только как `git config user.name` для автора.
Мотивация — proposal.md, поведение — `specs/site-comments/spec.md`.

## Goals / Non-Goals

**Goals:**
- Апрув строки и пуш журнала со страницы без терминала, с предсказуемым git-поведением на рабочей
  копии, в которой параллельно есть чужие (агентские) правки.

**Non-Goals:**
- Не разрешаем конфликты автоматически и не делаем force-push.
- Не проверяем, что человек апрувит свою строку: выделение строки — и есть подтверждение, а в
  коммите виден git-автор.
- Нет отмены апрува кнопкой, нет других статусов (Changes requested и т. п.) — одна кнопка и одно
  `set`.
- Не создаём ветки и MR: пуш — в upstream текущей ветки.
- Не меняем плагин openspec: колонка «Ожидает» уже читает `review.md` через `whenEmpty`.

## Decisions

- **Ключи внутри `comments`.** `approve` и `push` относятся к файлу журнала и без него смысла не
  имеют. `push` отдельным ключом, а не флагом в `approve`: апрув пушит всегда (в этом его смысл), а
  `push` включает плашку Push и задаёт шаблон сообщения общий для обоих действий.
- **Колонки по названиям, не по номерам.** `who` и ключи `set` — заголовки колонок таблицы: таблица
  статусов в шаблонах проектов меняется (колонки добавляют), а `cells` журнала замечаний уже
  позиционные — смешивать подходы в одной таблице не нужно. Сравнение заголовков — через `plain`
  (без разметки, регистр не важен).
- **Строка находится по всем ячейкам.** Клиент шлёт `page` и тексты ячеек строки, как DELETE; сервер
  ищет в таблице раздела `approve.heading` ровно одну строку с такими ячейками (через `plain`). Нет или
  несколько — 409 «reload the page». Альтернатива — по значению `who` — отвергнута: одно имя бывает в
  двух строках (человек в двух ролях).
- **Подстановки `set`.** `{date}` — локальная дата, как в `remarkVars`; `{author}` — имя из колонки
  `who` этой строки. Значения экранируются как ячейки журнала (`escapeHtml`, `|`).
- **Подпись по умолчанию — Approve row / «Одобрить строку».** В панели пачки агенту уже есть
  **Approve** / «Одобрить», а спека запрещает подписям у выделения совпадать с ней. Проекту, которому
  нужно ровно «Approve», — `buttons.approve` (своя подпись — ответственность проекта, как у
  остальных `buttons`). Кнопка плашки — **Push** / «Запушить», ключ `buttons.push`.
- **Модуль `src/core/reviewgit.ts`** — git-операции над одним файлом через `execFile('git', …)` без
  shell, `cwd` — корень проекта, окружение `GIT_TERMINAL_PROMPT=0` (пуш не повиснет на вопросе о
  пароле), таймаут на команду. Последовательность:
  1. preflight — до любых правок файла (апрув без upstream не должен оставить изменённый файл), все
     отказы — 409: нет незавершённого merge/rebase/cherry-pick/revert (`--git-path` `MERGE_HEAD`,
     `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge`, `rebase-apply`); ветка, а не detached HEAD;
     upstream задан, это ветка с тем же именем (как `push.default=simple`: иначе `review-x` с
     upstream `origin/master` пушилась бы в `master`) и она резолвится (`rev-parse --verify @{u}`);
     незапушенные коммиты `@{u}..HEAD` — без merge-коммитов и трогают только этот журнал (`log -z
     --name-only`). Исключение для коммитов журнала нужно для повтора после отклонённого пуша;
  2. апрув — запись ячеек; содержимое до правки запоминается;
  3. `git commit --only -m <msg> -- <file>`, если `git status --porcelain -- <file>` не пуст:
     `--only` берёт рабочую версию только этого файла и не трогает остальной индекс. Коммит не удался
     (hook, `index.lock`) — прежнее содержимое файла возвращается;
  4. если HEAD опережает upstream: `git fetch`; если upstream не предок HEAD — перенос (ниже);
  5. `git push <remote> HEAD:<branch>` — явная форма не зависит от `push.default`; без force.
- **Перенос на ушедший вперёд upstream — без rebase и stash.** Первая версия делала
  `rebase --autostash`, и у неё нашлись молчаливые сбои: autostash не восстанавливает индекс (staged
  правки становились unstaged), при конфликте применения stash rebase выходит с 0 и оставляет правки
  в общем stash, а сохранение индекса патчем ломалось на больших и новых файлах. Раз preflight
  гарантирует, что незапушенные коммиты — только журнала, перенос делается так: файл журнала
  сливается трёхсторонне (`git merge-file`: общий предок, HEAD, upstream; конфликт — 409), дерево
  upstream с этим журналом собирается во временном индексе (`GIT_INDEX_FILE`, `read-tree`,
  `update-index --cacheinfo`, `write-tree`), коммит — `commit-tree -p @{u}` с сообщением последнего
  коммита журнала, рабочая копия переключается `git checkout -B <branch> <commit>`. Checkout сам
  переносит локальные правки и индекс как есть и отказывает целиком, если они пересекаются с
  изменениями upstream (тогда 409, ничего не изменено). Несколько коммитов журнала сливаются в один.
  Альтернатива `git pull --rebase --autostash` всегда — отвергнута по тем же причинам.
- **Очередь git-операций.** Сервер выполняет git-операции строго по одной (promise-цепочка): две
  вкладки, нажавшие Push одновременно, иначе сталкиваются на `index.lock`.
- **Маршруты.** `POST /__c4builder/review-log/approve` и `POST /__c4builder/review-log/push` — рядом
  с маршрутами журнала, те же проверки `fromSite`/`localHost` и `localSources(page)`; регистрируются,
  только если задан соответствующий ключ (иначе 404 естественным образом). Ответ:
  `{ file, commit, pushed, message }`; ошибки — `{ error }` на английском, с хвостом stderr git.
- **`{change}`, `{action}`, `{author}`, `{file}` в сообщении.** `{change}` — имя каталога файла
  журнала (у OpenSpec — имя change), `{action}` — `approved` или `comments`, `{author}` — у апрува
  имя из `who`, у пуша — автор комментариев (`comments.author`, иначе git user.name), `{file}` — путь
  журнала от корня проекта.
- **Плашка Push журнала, только на страницах change'а.** Внизу по центру, как панель пачки агенту,
  но цветом журнала; при видимой панели агента — над ней. Видна, пока у журнала страницы есть что
  пушить. Состояние — с сервера: GET журнала при включённом `push` отвечает
  `pending: { changed, unpushed } | null` (`git status` файла и число незапушенных коммитов журнала;
  null — пушить нельзя: не git, нет upstream, чужие коммиты, merge в процессе). GET идёт при каждой
  отрисовке страницы (загрузка, переход, livereload) и после комментария, удаления, апрува и пуша —
  так плашка видит ручные правки `review.md`, застрявший коммит апрува и другие вкладки. Чтение
  состояния идёт через ту же очередь, что git-операции: GET, пришедший во время пуша, ждёт его конца.
  Отвергнуто:
  - липкий тост с **Push** и состоянием в `sessionStorage` (первая версия) — не видит ручных правок
    и застрявших коммитов; кнопка оставалась видимой и активной после успешного пуша: livereload
    после записи журнала перезагружал страницу посреди запроса, обработчик ответа старой страницы,
    очищавший состояние, погибал, новая страница восстанавливала тост из `sessionStorage`; так же
    GET во время пуша (не через очередь) отвечал «не запушено», и кнопка апрува оставалась у
    одобренной строки;
  - кнопка Push в окне комментария — пушит до того, как набраны все комментарии, и не видна, если
    журнал правили руками;
  - плашка сверху страницы — перекрывает заголовок и навигацию docsify и далеко от места действия.
- **Кнопки на время запроса.** Push и Approve row неактивны, пока идёт запрос (нет двойного
  коммита). После успеха плашка скрывается сразу, кнопка апрува у одобренной строки — до перерисовки
  страницы; ответ сервера подтверждает это перезапросом GET.
- **Клиент: условие кнопки апрува.** Только если GET журнала ответил `log: true`; `closest('tr')`
  у обоих концов выделения совпадает, таблица лежит в разделе `approve.heading`; индексы колонок
  берутся из `thead`. Ячейки строки и проверка «уже одобрено» — на клиенте по тексту ячеек; сервер
  проверяет заново.

## Risks / Trade-offs

- [В журнал попадут правки агента вместе с ручными — отличить их нельзя] → коммитится файл целиком;
  плашка и ответ называют файл; документация предупреждает.
- [Незапушенная работа агента уехала бы вместе с журналом] → preflight отказывает, если в ветке
  есть незапушенные коммиты кроме журнала; stash и rebase не используются, индекс не трогается.
- [Pre-commit hook проекта падает или долго работает] → хуки не отключаем; ошибка хука — ответ с
  выдержкой stderr, правка апрува откатывается, таймаут на коммит больше, чем на остальные команды.
- [Пуш требует пароля / ssh-passphrase без агента] → `GIT_TERMINAL_PROMPT=0` и таймаут; ошибка
  объясняет, что git должен пушить без ввода пароля.
- [Чужая строка одобрена по ошибке] → подпись и строка видны при выделении; откат — `git revert`,
  в коммите git-автор.

## Migration Plan

Ключи опциональны, без них поведение прежнее. Проекту (например, репозиторию спецификаций с OpenSpec) — добавить в
`.c4builder`:
`"comments": { …, "approve": { "heading": "Статусы", "who": "Кто", "set": { "Статус": "Approved", "Дата": "{date}" } }, "push": {} }`
и при желании `"buttons": { "approve": "Approve" }`. Откат — убрать ключи.

## Уточнения при реализации

- Коды ответов: 409 — отказ preflight, устаревшая или неоднозначная строка, строка без имени или уже
  одобренная (и коммит запушен), конфликт при переносе; 502 — fetch или push отклонены (коммит
  локальный; текст ошибки не называет кнопку — у апрува без `push` кнопки Push нет); 500 — колонки из
  `who`/`set` нет в таблице (ошибка конфига) и прочие сбои git.
- Повторный апрув: GET журнала с ключом `approve` отвечает `unpushed` — есть ли незапушенный коммит
  журнала (preflight проходит, ветка опережает upstream). Тогда кнопка видна и у уже одобренной
  строки; сервер, получив одобренную строку при `unpushed`, только дотолкает коммит (`pushPending`),
  без нового коммита и без правки файла.
- Ячейки строки на клиенте собираются без служебных элементов (`.c4b-del`, номера-ссылки, кнопки):
  если раздел журнала охватывает таблицу статусов, её строки получают «×».
- Fetch и перенос пропускаются, если HEAD не опережает `@{upstream}` после коммита: ответ
  `{ commit: null, pushed: false }`.
- Неотслеживаемый журнал перед `commit --only` добавляется `git add` (при неудаче коммита
  добавление снимается): `--only` знает лишь отслеживаемые пути.
- Шаблон сообщения коммита подставляется общим `fillCells`, строка таблицы ищется общим
  `findRowByCells` (удаление и апрув).
