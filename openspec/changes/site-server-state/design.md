# Design

## Context

Мотивация — proposal.md (Why). Текущее состояние:

- `src/cli/commands/site.ts` слушает `127.0.0.1:<port>` (`-p` или `WEB_PORT`), на `EADDRINUSE`
  подсказывает свободный порт и выходит (change `site-port-busy-hint`). Обработчиков сигналов нет:
  Ctrl+C завершает Node без события `exit`.
- Защита служебных запросов команд — `fromFeedbackCommand` (локальный `Host`, без `Origin`, заголовок
  `X-C4builder-Feedback: 1`) — объявлена внутри блока `-w`; там же состояние ящиков `agentState()`.
- `feedback.ts:31` и `doctor.ts:590` берут порт из `-p`/`webPort`; doctor отличает `site -w` от
  чужого процесса по `GET /__livereload` (SSE).
- Рядом с конфигом уже живут `<конфиг>.lock` и `<конфиг>.cache`; watch игнорирует пути с префиксом
  `configPath` (`dispatch.ts`, фильтр watcher'а) — файл `<конфиг>.server.json` под него попадает.

## Goals / Non-Goals

**Goals:**
- Любой клиент CLI находит сервер своего проекта без `-p`, а скилл — без `curl`.
- Отличать живой сервер этого проекта от оставшегося файла и от чужого процесса на порту.

**Non-Goals:**
- Автовыбор порта сервером. Теперь он технически возможен (клиенты читают порт из файла), но
  меняет контракт change'а `site-port-busy-hint` и привычный человеку адрес — отдельным change'ем.
- Управление сервером (`status --stop` и т. п.) и прогресс фонового рендера в `status`.

## Decisions

- **D1. Файл рядом с конфигом: `<конфиг>.server.json`.** Как `.lock` и `.cache`: у каждого worktree
  свой файл без ключей и хешей, агент может прочитать его сам, `-c other.c4builder` даёт отдельный
  файл. Альтернатива — `os.tmpdir()/c4builder-<hash(cwd)>.json`: нет шума в git, но файл не найти
  руками и разные пути у Docker/хоста; отвергнута. Шум закрываем `.gitignore` шаблона и репозитория.
- **D2. Содержимое:** `{ port, url, pid, version, watch, startedAt }`. `url` —
  `http://localhost:<port>`, как печатает `go to`. Запись — во временный файл и `rename` (читатель
  не увидит половину JSON), сразу после настоящего `listen` и до `resolve(server)`.
- **D3. Удаление — в `process.on('exit')` синхронным `rmSync`, только если в файле наш `pid`.**
  Чтобы `exit` наступал и по сигналам, `dispatch.ts` в режиме сервера ставит обработчики `SIGINT`,
  `SIGTERM`, `SIGHUP` → `process.exit(128 + n)`. Проверка `pid` защищает от гонки двух запусков:
  проигравший не удалит файл победителя.
- **D4. Живость — `pid` жив и `GET /__c4builder/status` на порту из файла отвечает тем же `pid`**
  (таймаут 1 с). Только `kill(pid, 0)` — ложное «жив» при переиспользованном pid; только проба
  порта — не отличить сервер этого проекта от сервера соседнего worktree на том же порту.
  Недействительный файл читатели игнорируют и не удаляют (`status`, `doctor` только читают); его
  перезапишет следующий сервер.
- **D5. Эндпоинт `GET /__c4builder/status` — во всех режимах сервера.** `localHost` и
  `fromFeedbackCommand` выносятся из блока `-w`, чтобы защита была общей. Ответ без `-w`:
  `watch: false`, `agent.on: false`, пустые `listeners`, `unaddressed: 0`. Заголовок прежний
  (`X-C4builder-Feedback`): это заголовок всех запросов команд CLI, новый не нужен.
- **D6. Выбор порта клиентом — общий модуль `src/cli/server-state.ts`:** `-p` → действительный файл
  → `webPort`; возвращает порт и источник (`flag` / `state` / `config`). Явный `-p` побеждает файл:
  человек мог намеренно указать другой сервер. Модуль читает конфиг как JSON без Configstore (как
  `feedback` сейчас) — `status` и `feedback` не создают файлов.
- **D7. Второй сервер — проверка в `dispatch.ts` до лока и сборки:** иначе повторный запуск сначала
  пересобрал бы `dist`, который раздаёт первый сервер. С `--open-change <id>` проверяем страницу тем
  же `PAGE_PATH?as=<id>`, что и `feedback`: 404 — прежнее предупреждение, адрес всё равно
  открывается. Без `--open*` — код 1: процесс, ожидавший запустить сервер, его не запустил.
- **D8. `c4builder status`:** текст — строка `site is running at <url> (pid N, c4builder V, watch)`,
  агентский режим, слушатели `name — listening|reconnecting, N queued`, пачки без адресата; JSON —
  `{ running, url, port, source, pid, version, watch, agent, listeners, unaddressed }`, при
  `running: false` — `{ running, port, source, busy }` (`busy` — порт занят чужим процессом). Код 0/1
  — скилл проверяет сервер одним вызовом. Без файла: проба `/__c4builder/status` на порту; 404 и SSE
  на `/__livereload` — сервер старой версии, `running: true` без подробностей.
- **D9. `doctor runtime` и `feedback` — через D6;** в doctor адрес и источник порта видны в
  сообщении. Подсказка агентского режима сервера про `-p` остаётся: она верна и без файла
  (каталог только для чтения).

## Risks / Trade-offs

- [Каталог проекта только для чтения — файл не записать] → предупреждение одной строкой, сервер
  работает, клиенты откатываются на `-p`/`webPort` (поведение до change'а).
- [`SIGKILL`, падение Node, `taskkill` на Windows — файл остаётся] → D4: файл недействителен, пока
  сервер с тем же `pid` не ответит; следующий запуск его перезапишет.
- [Два запуска одновременно проходят проверку D7] → один получит занятый порт, или оба поднимутся
  на разных `-p`; файл — у последнего записавшего, удаление по `pid` (D3) не трогает чужой. Редкий
  случай, без лока.
- [Файл в рабочем дереве существующих проектов] → строка в CHANGELOG и на странице CLI: добавить
  `.c4builder.server.json` в `.gitignore`; шаблон `--new` получает её сразу.
- [Эндпоинт раскрывает имена слушателей] → только запросы команд CLI с локальным `Host` (D5), как
  `/__c4builder/feedback/next`.

## Migration Plan

Миграции нет: старые клиенты продолжают работать по `-p`/`webPort`, новые клиенты со старым
сервером — по `webPort` (D8). Откат — revert; оставшиеся файлы состояния никто не читает.
